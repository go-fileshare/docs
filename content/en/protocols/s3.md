```hcl
serve "s3" { addr = "0.0.0.0:9000" }
```

Or over HTTPS, since v0.9.0, with `tls = true` and a
[`tls` block]({{< relref "/security/tls.md" >}}):

```hcl
serve "s3" {
  addr = "0.0.0.0:9000"
  tls  = true
}
```

The fifth protocol, and the one that makes an image reachable from anything
that speaks object storage — a backup tool, a data pipeline, `rclone`, a
browser's `fetch()`. **Nothing mounts.**

```
GET /                      the shares this person may use, as buckets
GET /photos?list-type=2    the files in that share, as keys
GET /photos/holiday.jpg    the file itself, Range and all
```

## A share is a bucket

Served over the **same per-user tree SFTP uses**: a filesystem whose top level
is the shares this person may use. So a share alice may not use is not a bucket
alice can see, and the access rules are applied in one place rather than copied
into a second protocol.

{{< callout type="info" >}}
**A directory inside a share is a prefix, not an object**

Which is what S3 clients already believe — they display prefixes ending in
the delimiter as folders. `GET` of a directory answers `NoSuchKey`, because
answering 200 would make a client think it can fetch the bytes of a folder.
{{< /callout >}}

## An access key is a user; the secret key is their password

```sh
export AWS_ACCESS_KEY_ID=alice
export AWS_SECRET_ACCESS_KEY=$(cat alice.pw)
aws --endpoint-url http://attic.example.org:9000 s3 ls
```

SigV4 proves possession of the secret by computing an HMAC from it — the
password never crosses the wire, exactly as with NTLMv2.

{{< callout type="error" >}}
**So the directory must HOLD the password, not merely check it**

A source that can only *verify* a password — an LDAP bind, a bcrypt column
— can answer WebDAV and **cannot** answer S3.

And not an NT hash either: that is the MD4 SMB can work from, and an HMAC
cannot be computed from it. **An identity holding only an NT hash serves
SMB and not S3** — near neighbours rather than the same answer.
[`check`]({{< relref "/configuration/check.md" >}}) prints the column.
{{< /callout >}}

⛔ There is no `Password()` accessor anywhere in the program: the password is
reached only through `Identity.Derive`, which takes a derivation and returns
its result. For S3 the derivation is the identity, because SigV4's key
schedule lives in go-filesystems/s3; the secret goes to that signature check
for that one user and nowhere else.

## What is served

`ListBuckets`, `HeadBucket`, `ListObjectsV2` with prefix, delimiter, max-keys
and continuation, `HeadObject`, and `GetObject` with `Range`. SigV4 in both
forms, header and presigned.

The object API itself is
[`go-filesystems/s3`](https://github.com/go-filesystems/s3).

## What is refused, and why

{{< callout type="warning" >}}
**Writes answer 403**

`PUT`, `POST` and `DELETE` are refused with `AccessDenied` ("this export is
read-only"). fileshare keeps the S3 server read-only because a share a person
may only read has to refuse at the same place SFTP does, and that is not
wired yet; go-filesystems/s3 v0.3.0, which this release is built on, refuses
every write anyway. Refusing beats a half-written object.
{{< /callout >}}

{{< callout type="warning" >}}
**A bearer token is not accepted here**

[OIDC]({{< relref "/protocols/webdav.md" >}}) works over WebDAV and nowhere else. S3 authenticates with
a SigV4 signature — an HMAC over the request, with no field a bearer token
fits in.

The route is STS `AssumeRoleWithWebIdentity`, which exchanges an OIDC
token for temporary credentials the client then signs with. It is served on
this listener since v0.50.0: see [below](#sts).
{{< /callout >}}

Multipart upload, versioning, ACLs, policies, lifecycle rules, replication and
tagging are not implemented. Setting any of them, and starting a multipart
upload, is a write, and answers `AccessDenied` like any other. A `GET` that
asks for one of them (`?versioning`, `?acl`, `?tagging`...) is not told apart:
the query is ignored and the bucket's listing or the object is returned.
`NotImplemented` answers a listing other than `list-type=2`, any method but
`GET` on `/`, and a method no operation here uses.

## Temporary credentials: STS `AssumeRoleWithWebIdentity` {#sts}

Since v0.50.0 the S3 listener also answers the AWS STS API
(`AssumeRoleWithWebIdentity`, version 2011-06-15): a token from the
[`oidc` block]({{< relref "/protocols/webdav.md" >}})'s provider is exchanged for an access key, a secret
key and a session token that **expire**. `aws`, `rclone` and the AWS SDKs speak
it as they do to AWS, and nobody holds a password.

```hcl
oidc {
  issuer   = "https://login.example.org"
  audience = "fileshare"
}

serve "s3" {
  addr             = "0.0.0.0:9000"
  tls              = true
  sts              = true      # POST / with Action=AssumeRoleWithWebIdentity
  sts_duration     = "1h"      # the default, 15m to 12h
  sts_max_duration = "4h"      # the most DurationSeconds may ask; defaults to sts_duration
  static_keys      = false     # no more access-key-is-a-user: only temporary credentials sign
}
```

- **The token** is an access token (`typ` `at+jwt`) from the `oidc` block's
  provider, for that block's issuer and audience — there is no second provider
  configuration. A person's token, or a machine's: go-authn/bridge's
  `client_credentials` token for a client that authenticates with a private key
  (`private_key_jwt`) has `sub` = the client ID, which is the name here.
- ⛔ **It passes the same rule as a token over WebDAV.** A valid token for a name
  no source here knows is refused unless `trust_all = true` or a share's `oidc:`
  rule names it (`allow = ["oidc:user:winpc-17"]`). The share's rules then
  decide what is visible.
- **The answer** is `AccessKeyId` (`ASIA…`), `SecretAccessKey`, `SessionToken`
  and `Expiration`. Requests are signed with them and carry the session token in
  `x-amz-security-token`, **signed**. They are random, kept in memory only and
  never written; a restart ends them and the client asks again.
- ⛔ **Lifetime = min(requested, what the token has left).** The credentials never
  outlive the token that bought them (`sts_duration`, or `DurationSeconds` up to
  `sts_max_duration`, is only the ceiling). A token with **less than 6 minutes**
  left is refused with `ExpiredTokenException`: the AWS SDKs renew about 5
  minutes before `Expiration`, and shorter credentials would be renewed at once,
  for ever. A client presents a fresh token at each exchange.
- ⛔ **A session is judged at every request**: it expires; its session token is
  bound to its access key; it ends when the provider revokes the person after the
  token was issued ([shared signals]({{< relref "/security/shared-signals.md" >}}));
  and when the configuration stops admitting the name.
- `Policy`, `PolicyArns` and a second `WebIdentityToken` are refused, and the
  parameters must be in the POST body, never the URL.
- **`static_keys = false`** turns the access-key-is-a-user, secret-key-is-the-password
  way off. It needs `sts = true`: the configuration is refused at load otherwise,
  since a listener nobody could sign for would look configured. Over a
  non-loopback address `sts` needs `tls = true`, or `plaintext = true` when TLS
  is terminated in front.

### On an unattended machine: awscred

[`awscred`](https://github.com/go-authn/awscred) v0.1.0 is an AWS
`credential_process` for machines that hold a private key and no password: it
signs a `private_key_jwt`, gets a token from go-authn/bridge, calls this
endpoint and prints the credentials as the SDKs read them. The SDKs run it
again before `Expiration`.

```ini
[profile fileshare]
credential_process = awscred --issuer https://login.example.org --client winpc-17 --key /etc/awscred/winpc-17.pem --sts https://s3.example.org
```

⛔ On Unix `awscred` refuses a key file readable by group or others
(`chmod 600`). On Windows file modes mean nothing: keep the key in the service
account's profile or in a directory whose ACL admits that account only. A key in
the Windows CNG store or a TPM is not supported yet.

### Behind a proxy: `trusted_proxies`

Behind the proxy that `plaintext = true` is for, every client would be one
source for the rate limits below. Name the proxies, on the `s3` serve block:

```hcl
serve "s3" {
  addr            = "127.0.0.1:9000"
  plaintext       = true
  sts             = true
  trusted_proxies = ["10.0.0.2", "10.0.1.0/29"]
}
```

Only a request arriving **from** a trusted proxy is believed about its client,
by the right-most `X-Forwarded-For` hop that is not itself a trusted proxy; from
anybody else the header is ignored.

{{< callout type="warning" >}}
**The list must name the proxies and nothing else**

A prefix wider than one host (a `/24`, an IPv6 `/64`) is accepted — a pool of
proxies, a `/29`, is legitimate — and a warning is printed at start: a client
that can have an address inside it chooses its own `X-Forwarded-For`, and with
it the bucket it is counted in.
{{< /callout >}}

### Limits

- **16 sessions per name**: the oldest of the same name goes first, another
  name's sessions stay (20000 in all).
- **60 requests a minute per source address**, answered `429 Throttling`. Every
  request counts, valid or not, before the token is verified. A source is an
  IPv4 address, or an IPv6 **/64**.
- The count is O(1) per request, under its own lock, in a sliding minute made
  of two generations; the credentialed S3 requests never wait for it.
- A source seen in the last minute is counted as long as the table holds fewer
  than **2 × 10000** entries (the bound, however long a flood lasts). A source
  the full table has not seen is counted in an overflow bucket of its network —
  its **/48** (IPv6) or **/24** (IPv4), ten times the rate each — so a flood
  exhausts the buckets of the networks it comes from, not everybody's. IPv4
  neighbours behind one /24 (CGNAT, a campus) share one bucket.
- ⛔ **Past 1024 networks a minute, one shared bucket serves the rest**: an
  attacker holding more networks than that exhausts it, and every source the
  table has not already seen — **existing clients that renew about hourly
  included** — is refused until the minute turns. That is this design's limit.

## Two limits worth knowing before pointing it at something large

**`GetObject` reads the whole object into memory.** The driver interface offers
`ReadFile` and nothing else — no opener, no reader — so there is no streaming
read to use. A bound, 256 MiB, answers `EntityTooLarge` rather than taking
the process down.

**`LastModified` is the epoch.** `filesystem.Stat` carries `Mode`, `Size` and
`Inode`, and no modification time at all. The field is not optional in the S3
schema, so something must be sent; the epoch is obviously not a real time,
where `time.Now()` would look like a file that just changed and make every sync
tool copy everything, every run.
