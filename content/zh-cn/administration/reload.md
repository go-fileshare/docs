```hcl
reload = "5m"   # 同时在收到 SIGHUP 和管理 API 的 ReloadDirectory 时重新加载
```

人员来自目录服务，而其他系统会修改这些目录服务：go-authn/bridge 会把
应用密码写入某张表，并在人员被停用时删除该行。如果不重新加载，服务器只会为
启动时存在的人员提供服务。自 v0.10.0 起，服务器会重新读取它们：

- 每隔一个 `reload` 间隔，该间隔是**至少一秒**的 Go 持续时间，因为一个
  每秒被读取许多次的目录服务只会给别人的数据库增加负载，并不会让服务器更新；
- 收到 **`SIGHUP`** 时（Unix）；
- 调用[管理 API]({{< relref "/administration/_index.md" >}}) 的 **`ReloadDirectory`** 时，它会应答
  哪些人被添加、移除和更改，是否启动了新的世代，并附上
  值得阅读的提示：不再存在或没有成员的组，以及共享所指明但
  已不在目录服务中的人员。

未设置 `reload` 时，仅在启动时、收到 `SIGHUP` 时以及调用
`ReloadDirectory` 时读取目录服务。

被重新读取的是 `users` 块（SQL、LDAP）。配置文件中的 `user` 和
`group` 块**本身就是**配置，在启动时读取。

## 重新加载会做什么，取决于什么发生了变化 {#what-a-reload-does-depends-on-what-changed}

界线划在**撤销**上：

| 发生了什么变化 | 会发生什么 |
|---|---|
| **只有新增**：新来的人，其加入不会改变任何共享的展开列表（新的应用密码，或共享通过 `oidc:` 规则触及的人员，或根本不涉及任何共享的人员） | **原地**添加，包括 SMB 正在运行的服务器，**不触及任何连接**。桥接程序整天创建应用密码也不会打扰任何人。 |
| **任何被收回的内容**：有人离开、凭据更改、某个共享的展开列表发生变化 | 一个**新世代**，旧世代的连接被**关闭**，与[管理变更]({{< relref "/administration/_index.md#a-change-is-a-new-generation" >}})完全一样。比其主人被移除后仍然存活的会话，正是重新加载要终结的对象。 |
| **无法读取的目录服务**：数据库无法访问，查询失败 | **不发生任何变化**。故障不应当清空一台文件服务器，而“没有任何人”正是读取失败时的表象。 |

加入某个共享所指明的组的新人*确实*会改变该共享，并像对它的任何其他变更一样
经历一个新世代：SMB 在启动时就固定了共享的列表。

如果共享指明了已经离开的人，或不再存在或不再有任何成员的组（自 v0.29.1 起可区分这两种情况），
则会**不含这些人员或这些组**地提供服务（这是安全的方向）并予以说明，而不是像
启动时那样被拒绝：拒绝会保留旧列表，而旧列表正是
刚刚被收回的访问权限。

## 空组不等于所有人 {#an-empty-group-is-not-everyone}

{{< callout type="error" >}}
**为 `@engineers` 编写的共享，在最后一位工程师离开后，不会向任何人提供服务**

空的 `allow` 表示“任何通过身份验证的人”。因此决定
共享是否开放的是**所写的内容**，而不是它现在展开成什么：为某个组
编写的共享，在该组清空后仍然保持关闭。这样的共享
根本不会通过 SMB 提供，因为其空的 `AllowUsers` 会被理解为
所有人。
{{< /callout >}}

## 观察它 {#watching-it}

`fileshare_directory_reloads_total{result}` 统计这样的重新加载：未发现任何变化
（`unchanged`）、原地添加（`added`）、启动了一个世代（`swapped`）或
无法读取目录服务（`failed`）；`fileshare_directory_people` 是最近一次读取时
所含的人数。参见[健康检查与指标]({{< relref "/administration/health.md" >}})。

{{< callout type="info" >}}
**重新加载触及不到的对象**

由身份提供方通过令牌或证书担保的人员
不在目录服务中，因此重新加载与这些人员无关。收回**这些人员**的访问权限
是[撤销列表和共享信号]({{< relref "/security/_index.md" >}})的工作。
{{< /callout >}}
