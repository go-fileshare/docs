```hcl
serve "s3" { addr = "0.0.0.0:9000" }
```

또는 v0.9.0부터 `tls = true`와 [`tls` 블록]({{< relref "/security/tls.md" >}})으로
HTTPS 위에서도 제공할 수 있습니다.

```hcl
serve "s3" {
  addr = "0.0.0.0:9000"
  tls  = true
}
```

다섯 번째 프로토콜이며, 백업 도구, 데이터 파이프라인, `rclone`, 브라우저의
`fetch()` 등 오브젝트 스토리지를 사용하는 무엇에서든 이미지에 접근할 수 있게
합니다. **마운트는 없습니다.**

```
GET /                      the shares this person may use, as buckets
GET /photos?list-type=2    the files in that share, as keys
GET /photos/holiday.jpg    the file itself, Range and all
```

## 공유는 버킷입니다 {#a-share-is-a-bucket}

**SFTP가 사용하는 것과 같은 사용자별 트리**를 통해 제공됩니다. 최상위가 해당
사용자가 이용할 수 있는 공유인 파일 시스템입니다. 따라서 alice가 이용할 수 없는
공유는 alice가 볼 수 있는 버킷이 아니며, 접근 규칙은 두 번째 프로토콜에 복사되지
않고 한곳에서 적용됩니다.

{{< callout type="info" >}}
**공유 안의 디렉터리는 오브젝트가 아니라 프리픽스입니다**

S3 클라이언트가 이미 그렇게 알고 있는 방식입니다. 구분자로 끝나는 프리픽스를
폴더로 표시합니다. 디렉터리에 대한 `GET`은 `NoSuchKey`로 응답합니다. 200으로
응답하면 클라이언트가 폴더의 바이트를 가져올 수 있다고 생각하게 되기 때문입니다.
{{< /callout >}}

## 액세스 키는 사용자이고, 시크릿 키는 그 사용자의 비밀번호입니다 {#an-access-key-is-a-user-the-secret-key-is-their-password}

```sh
export AWS_ACCESS_KEY_ID=alice
export AWS_SECRET_ACCESS_KEY=$(cat alice.pw)
aws --endpoint-url http://attic.example.org:9000 s3 ls
```

SigV4는 비밀로부터 HMAC을 계산하여 비밀을 가지고 있음을 증명합니다. NTLMv2와
똑같이 비밀번호는 네트워크를 건너지 않습니다.

{{< callout type="error" >}}
**그래서 디렉터리는 비밀번호를 확인하는 데 그치지 않고 보유해야 합니다**

비밀번호를 *검증*만 할 수 있는 소스(LDAP 바인드, bcrypt 열)는 WebDAV에는
응답할 수 있지만 S3에는 **응답할 수 없습니다**.

NT 해시도 안 됩니다. 그것은 SMB가 사용할 수 있는 MD4이고, 거기서 HMAC을 계산할
수는 없습니다. **NT 해시만 가진 ID는 SMB로는 제공되지만 S3로는 제공되지
않습니다.** 서로 가까운 이웃일 뿐 같은 답이 아닙니다.
[`check`]({{< relref "/configuration/check.md" >}})가 해당 열을 출력합니다.
{{< /callout >}}

⛔ 프로그램 어디에도 `Password()` 접근자는 없습니다. 비밀번호는 오직
`Identity.Derive`를 통해서만 접근되며, 이는 파생 함수를 받아 그 결과를 돌려줍니다.
S3의 경우 SigV4의 키 스케줄이 go-filesystems/s3에 있으므로 파생 함수는 항등
함수입니다. 비밀은 그 한 사용자에 대한 서명 검사에만 전달되고 다른 어디에도
가지 않습니다.

## 제공되는 것 {#what-is-served}

`ListBuckets`, `HeadBucket`, 프리픽스, 구분자, max-keys, 연속 토큰을 지원하는
`ListObjectsV2`, `HeadObject`, 그리고 `Range`를 지원하는 `GetObject`입니다.
SigV4는 헤더 방식과 사전 서명 방식 두 가지를 모두 지원합니다.

오브젝트 API 자체는
[`go-filesystems/s3`](https://github.com/go-filesystems/s3)입니다.

## 거부되는 것과 그 이유 {#what-is-refused-and-why}

{{< callout type="warning" >}}
**쓰기는 403으로 응답합니다**

`PUT`, `POST`, `DELETE`는 `AccessDenied`("this export is read-only")로 거부됩니다.
fileshare가 S3 서버를 읽기 전용으로 유지하는 이유는, 사용자가 읽기만 할 수 있는
공유는 SFTP와 같은 지점에서 거부해야 하는데 아직 연결되지 않았기 때문입니다. 이
릴리스가 기반으로 하는 go-filesystems/s3 v0.3.0은 어차피 모든 쓰기를 거부합니다.
거부하는 편이 반쯤 쓰인 오브젝트보다 낫습니다.
{{< /callout >}}

{{< callout type="warning" >}}
**여기서는 베어러 토큰을 수락하지 않습니다**

[OIDC]({{< relref "/protocols/webdav.md" >}})는 WebDAV에서만 동작하고 다른 곳에서는
동작하지 않습니다. S3는 요청에 대한 HMAC인 SigV4 서명으로 인증하며, 베어러 토큰이
들어갈 필드가 없습니다.

일반적인 경로는 STS `AssumeRoleWithWebIdentity`로, OIDC 토큰을 클라이언트가 이후
서명에 쓰는 임시 자격 증명으로 교환합니다. 이는 다른 메커니즘이며 **구현되어 있지
않습니다**.
{{< /callout >}}

멀티파트 업로드, 버전 관리, ACL, 정책, 수명 주기 규칙, 복제, 태깅은 구현되어 있지
않습니다. 이들을 설정하는 것과 멀티파트 업로드를 시작하는 것은 쓰기이며, 다른
쓰기와 마찬가지로 `AccessDenied`로 응답합니다. 이들 중 하나를 요청하는
`GET`(`?versioning`, `?acl`, `?tagging`...)은 구별되지 않습니다. 쿼리는 무시되고
버킷의 목록이나 오브젝트가 반환됩니다. `list-type=2`가 아닌 목록, `/`에 대한
`GET` 이외의 모든 메서드, 여기서 어떤 작업도 사용하지 않는 메서드에는
`NotImplemented`로 응답합니다.

## 큰 대상에 연결하기 전에 알아 둘 두 가지 한계 {#two-limits-worth-knowing-before-pointing-it-at-something-large}

**`GetObject`는 오브젝트 전체를 메모리로 읽습니다.** 드라이버 인터페이스는
`ReadFile`만 제공하고, 오프너나 리더는 없으므로 사용할 스트리밍 읽기가 없습니다.
256 MiB라는 상한이 프로세스를 중단시키는 대신 `EntityTooLarge`로 응답합니다.

**`LastModified`는 에포크입니다.** `filesystem.Stat`은 `Mode`, `Size`, `Inode`를
담고 있으며 수정 시각은 전혀 없습니다. S3 스키마에서 이 필드는 선택 사항이 아니어서
무언가를 보내야 합니다. 에포크는 분명히 실제 시각이 아닌 반면, `time.Now()`는 방금
바뀐 파일처럼 보여서 모든 동기화 도구가 실행할 때마다 모든 것을 복사하게
만들 것입니다.
