```hcl
serve "s3" { addr = "0.0.0.0:9000" }
```

Oder über HTTPS, seit v0.9.0, mit `tls = true` und einem
[`tls`-Block]({{< relref "/security/tls.md" >}}):

```hcl
serve "s3" {
  addr = "0.0.0.0:9000"
  tls  = true
}
```

Das fünfte Protokoll, und dasjenige, das ein Image von allem aus erreichbar macht,
was Objektspeicher spricht – ein Backup-Werkzeug, eine Datenpipeline, `rclone`, das
`fetch()` eines Browsers. **Nichts wird eingehängt.**

```
GET /                      the shares this person may use, as buckets
GET /photos?list-type=2    the files in that share, as keys
GET /photos/holiday.jpg    the file itself, Range and all
```

## Eine Freigabe ist ein Bucket {#a-share-is-a-bucket}

Bereitgestellt über **denselben Baum pro Benutzer, den SFTP verwendet**: ein Dateisystem, dessen oberste Ebene
aus den Freigaben besteht, die diese Person nutzen darf. Eine Freigabe, die alice nicht nutzen darf, ist also kein Bucket,
den alice sehen kann, und die Zugriffsregeln werden an einer Stelle angewendet, statt
in ein zweites Protokoll kopiert zu werden.

{{< callout type="info" >}}
**Ein Verzeichnis innerhalb einer Freigabe ist ein Präfix, kein Objekt**

Genau das nehmen S3-Clients ohnehin an – sie zeigen Präfixe, die auf
das Trennzeichen enden, als Ordner an. Ein `GET` auf ein Verzeichnis antwortet mit `NoSuchKey`, weil
eine Antwort 200 einen Client glauben ließe, er könne die Bytes eines Ordners abrufen.
{{< /callout >}}

## Ein Access Key ist ein Benutzer; der Secret Key ist sein Passwort {#an-access-key-is-a-user-the-secret-key-is-their-password}

```sh
export AWS_ACCESS_KEY_ID=alice
export AWS_SECRET_ACCESS_KEY=$(cat alice.pw)
aws --endpoint-url http://attic.example.org:9000 s3 ls
```

SigV4 weist den Besitz des Geheimnisses nach, indem daraus ein HMAC berechnet wird – das
Passwort geht nie über die Leitung, genau wie bei NTLMv2.

{{< callout type="error" >}}
**Daher muss das Verzeichnis das Passwort HALTEN, nicht nur prüfen**

Eine Quelle, die ein Passwort nur *verifizieren* kann – ein LDAP-Bind, eine bcrypt-Spalte
–, kann WebDAV beantworten und **kann** S3 **nicht** beantworten.

Und auch kein NT-Hash: Das ist der MD4-Wert, mit dem SMB arbeiten kann, und ein HMAC
lässt sich daraus nicht berechnen. **Eine Identität, die nur einen NT-Hash hält, bedient
SMB und nicht S3** – nahe Nachbarn statt derselben Antwort.
[`check`]({{< relref "/configuration/check.md" >}}) gibt die Spalte aus.
{{< /callout >}}

⛔ Es gibt nirgends im Programm einen `Password()`-Accessor: Das Passwort wird
nur über `Identity.Derive` erreicht, das eine Ableitung entgegennimmt und
deren Ergebnis zurückgibt. Für S3 ist die Ableitung die Identität, weil der Schlüsselplan von SigV4
in go-filesystems/s3 liegt; das Geheimnis geht an diese Signaturprüfung
für diesen einen Benutzer und nirgendwo sonst hin.

## Was bereitgestellt wird {#what-is-served}

`ListBuckets`, `HeadBucket`, `ListObjectsV2` mit Präfix, Trennzeichen, max-keys
und Fortsetzung, `HeadObject` und `GetObject` mit `Range`. SigV4 in beiden
Formen, im Header und vorsigniert.

Die Objekt-API selbst ist
[`go-filesystems/s3`](https://github.com/go-filesystems/s3).

## Was abgelehnt wird, und warum {#what-is-refused-and-why}

{{< callout type="warning" >}}
**Schreibvorgänge antworten mit 403**

`PUT`, `POST` und `DELETE` werden mit `AccessDenied` („this export is
read-only“) abgelehnt. fileshare hält den S3-Server schreibgeschützt, weil eine Freigabe, die eine Person
nur lesen darf, an derselben Stelle ablehnen muss wie bei SFTP, und das ist noch nicht
verdrahtet; go-filesystems/s3 v0.3.0, auf dem dieses Release aufbaut, lehnt
ohnehin jeden Schreibvorgang ab. Ablehnen ist besser als ein halb geschriebenes Objekt.
{{< /callout >}}

{{< callout type="warning" >}}
**Ein Bearer-Token wird hier nicht akzeptiert**

[OIDC]({{< relref "/protocols/webdav.md" >}}) funktioniert über WebDAV und nirgendwo sonst. S3 authentifiziert mit
einer SigV4-Signatur – einem HMAC über die Anfrage, ohne ein Feld, in das ein Bearer-Token
passt.

Der Weg ist STS `AssumeRoleWithWebIdentity`, das ein OIDC-Token
gegen temporäre Zugangsdaten tauscht, mit denen der Client dann signiert. Er wird
seit v0.50.0 an diesem Listener bedient: siehe [unten](#sts).
{{< /callout >}}

Multipart-Upload, Versionierung, ACLs, Richtlinien, Lifecycle-Regeln, Replikation und
Tagging sind nicht implementiert. Eines davon zu setzen oder einen Multipart-Upload
zu beginnen, ist ein Schreibvorgang und antwortet wie jeder andere mit `AccessDenied`. Ein `GET`, das
nach einem davon fragt (`?versioning`, `?acl`, `?tagging`...), wird nicht unterschieden:
Die Query wird ignoriert, und das Listing des Buckets bzw. das Objekt wird zurückgegeben.
`NotImplemented` beantwortet ein anderes Listing als `list-type=2`, jede Methode außer
`GET` auf `/` und eine Methode, die keine Operation hier verwendet.

## Temporäre Zugangsdaten: STS `AssumeRoleWithWebIdentity` {#sts}

Seit v0.50.0 beantwortet der S3-Listener auch die AWS-STS-API
(`AssumeRoleWithWebIdentity`, Version 2011-06-15): Ein Token des Anbieters aus dem
[`oidc`-Block]({{< relref "/protocols/webdav.md" >}}) wird gegen einen Access Key, einen Secret Key und ein
Session-Token getauscht, die **ablaufen**. `aws`, `rclone` und die AWS-SDKs sprechen es
wie mit AWS, und niemand hält ein Passwort.

```hcl
oidc {
  issuer   = "https://login.example.org"
  audience = "fileshare"
}

serve "s3" {
  addr             = "0.0.0.0:9000"
  tls              = true
  sts              = true      # POST / mit Action=AssumeRoleWithWebIdentity
  sts_duration     = "1h"      # der Standard, 15m bis 12h
  sts_max_duration = "4h"      # das Meiste, was DurationSeconds verlangen darf; Standard: sts_duration
  static_keys      = false     # kein „Access Key ist ein Benutzer“ mehr: nur temporäre Zugangsdaten signieren
}
```

- **Das Token** ist ein Access Token (`typ` `at+jwt`) des Anbieters des `oidc`-Blocks, für
  Issuer und Audience dieses Blocks – es gibt keine zweite Anbieterkonfiguration. Das Token
  einer Person oder einer Maschine: Das `client_credentials`-Token von go-authn/bridge für einen
  Client, der sich mit einem privaten Schlüssel authentifiziert (`private_key_jwt`), hat
  `sub` = die Client-ID, und das ist hier der Name.
- ⛔ **Es durchläuft dieselbe Regel wie ein Token über WebDAV.** Ein gültiges Token für einen
  Namen, den hier keine Quelle kennt, wird abgelehnt, es sei denn `trust_all = true` oder die
  `oidc:`-Regel einer Freigabe nennt ihn (`allow = ["oidc:user:winpc-17"]`). Die Regeln der
  Freigabe entscheiden dann, was sichtbar ist.
- **Die Antwort** ist `AccessKeyId` (`ASIA…`), `SecretAccessKey`, `SessionToken` und
  `Expiration`. Anfragen werden damit signiert und tragen das Session-Token in
  `x-amz-security-token`, **signiert**. Sie sind zufällig, nur im Speicher und nie
  geschrieben; ein Neustart beendet sie, und der Client fragt erneut.
- ⛔ **Lebensdauer = min(angefragt, was das Token noch hat).** Die Zugangsdaten überleben nie das
  Token, das sie gekauft hat (`sts_duration` oder `DurationSeconds` bis `sts_max_duration` ist nur
  die Obergrenze). Ein Token mit **weniger als 6 Minuten** Rest wird mit `ExpiredTokenException`
  abgelehnt: Die AWS-SDKs erneuern etwa 5 Minuten vor `Expiration`, und kürzere Zugangsdaten
  würden sofort und immer wieder erneuert. Ein Client legt bei jedem Tausch ein frisches Token vor.
- ⛔ **Eine Sitzung wird bei jeder Anfrage beurteilt**: Sie läuft ab; ihr Session-Token ist an ihren
  Access Key gebunden; sie endet, wenn der Anbieter die Person nach Ausstellung des Tokens sperrt
  ([Shared Signals]({{< relref "/security/shared-signals.md" >}})); und wenn die Konfiguration den
  Namen nicht mehr zulässt.
- `Policy`, `PolicyArns` und ein zweites `WebIdentityToken` werden abgelehnt, und die Parameter
  gehören in den POST-Body, nie in die URL.
- **`static_keys = false`** schaltet den Weg „Access Key ist ein Benutzer, Secret Key ist das
  Passwort“ ab. Es braucht `sts = true`: Sonst wird die Konfiguration beim Laden abgelehnt, denn
  ein Listener, für den niemand signieren könnte, sähe konfiguriert aus. Über eine Adresse
  außerhalb von Loopback braucht `sts` `tls = true`, oder `plaintext = true`, wenn TLS davor
  terminiert wird.

### Auf einer unbeaufsichtigten Maschine: awscred {#on-an-unattended-machine-awscred}

[`awscred`](https://github.com/go-authn/awscred) v0.1.0 ist ein AWS-`credential_process` für
Maschinen mit privatem Schlüssel und ohne Passwort: Es signiert ein `private_key_jwt`, holt ein
Token von go-authn/bridge, ruft diesen Endpunkt auf und gibt die Zugangsdaten so aus, wie die SDKs
sie lesen. Die SDKs führen es vor `Expiration` erneut aus.

```ini
[profile fileshare]
credential_process = awscred --issuer https://login.example.org --client winpc-17 --key /etc/awscred/winpc-17.pem --sts https://s3.example.org
```

⛔ Unter Unix lehnt `awscred` eine Schlüsseldatei ab, die für Gruppe oder andere lesbar ist
(`chmod 600`). Unter Windows bedeuten Dateimodi nichts: Der Schlüssel gehört ins Profil des
Dienstkontos oder in ein Verzeichnis, dessen ACL nur dieses Konto zulässt. Ein Schlüssel im
Windows-CNG-Speicher oder in einem TPM wird noch nicht unterstützt.

### Hinter einem Proxy: `trusted_proxies` {#behind-a-proxy-trusted_proxies}

Hinter dem Proxy, für den `plaintext = true` da ist, wäre jeder Client für die Ratenbegrenzungen
unten eine einzige Quelle. Benennen Sie die Proxys im `s3`-serve-Block:

```hcl
serve "s3" {
  addr            = "127.0.0.1:9000"
  plaintext       = true
  sts             = true
  trusted_proxies = ["10.0.0.2", "10.0.1.0/29"]
}
```

Nur einer Anfrage, die **von** einem vertrauten Proxy kommt, wird zu ihrem Client geglaubt, und
zwar über den am weitesten rechts stehenden `X-Forwarded-For`-Hop, der nicht selbst ein vertrauter
Proxy ist; bei allen anderen wird der Header ignoriert.

{{< callout type="warning" >}}
**Die Liste muss die Proxys nennen und sonst nichts**

Ein Präfix, der mehr als einen Host umfasst (ein `/24`, ein IPv6-`/64`), wird akzeptiert – ein Pool
von Proxys, ein `/29`, ist legitim –, und beim Start wird eine Warnung ausgegeben: Ein Client, der
eine Adresse darin haben kann, wählt seinen eigenen `X-Forwarded-For` und damit den Eimer, in dem er
gezählt wird.
{{< /callout >}}

### Grenzen {#limits}

- **16 Sitzungen pro Name**: Die älteste desselben Namens geht zuerst, die Sitzungen anderer Namen
  bleiben (insgesamt 20000).
- **60 Anfragen pro Minute und Quelladresse**, beantwortet mit `429 Throttling`. Jede Anfrage zählt,
  gültig oder nicht, bevor das Token geprüft wird. Eine Quelle ist eine IPv4-Adresse oder ein
  IPv6-**/64**.
- Das Zählen ist O(1) pro Anfrage, unter einer eigenen Sperre, in einer gleitenden Minute aus zwei
  Generationen; die S3-Anfragen mit Zugangsdaten warten nie darauf.
- Eine in der letzten Minute gesehene Quelle wird gezählt, solange die Tabelle weniger als
  **2 × 10000** Einträge hält (die Schranke, egal wie lange eine Flut dauert). Eine Quelle, die die
  volle Tabelle nicht gesehen hat, wird in einem Überlauf-Eimer ihres Netzes gezählt – ihr **/48**
  (IPv6) oder **/24** (IPv4), je das Zehnfache der Rate –, sodass eine Flut die Eimer der Netze
  erschöpft, aus denen sie kommt, nicht die aller. IPv4-Nachbarn hinter einem /24 (CGNAT, ein
  Campus) teilen sich einen Eimer.
- ⛔ **Jenseits von 1024 Netzen pro Minute bedient ein gemeinsamer Eimer den Rest**: Ein Angreifer mit
  mehr Netzen erschöpft ihn, und jede Quelle, die die Tabelle nicht schon gesehen hat –
  **bestehende Clients, die etwa stündlich erneuern, eingeschlossen** – wird abgelehnt, bis die Minute
  umspringt. Das ist die Grenze dieses Entwurfs.

## Zwei Grenzen, die man kennen sollte, bevor man es auf etwas Großes richtet {#two-limits-worth-knowing-before-pointing-it-at-something-large}

**`GetObject` liest das ganze Objekt in den Arbeitsspeicher.** Die Treiberschnittstelle bietet
`ReadFile` und sonst nichts – keinen Opener, keinen Reader –, daher gibt es kein streamendes
Lesen, das man nutzen könnte. Eine Obergrenze von 256 MiB antwortet mit `EntityTooLarge`, statt
den Prozess zum Absturz zu bringen.

**`LastModified` ist die Epoche.** `filesystem.Stat` trägt `Mode`, `Size` und
`Inode` und überhaupt keine Änderungszeit. Das Feld ist im S3-Schema nicht optional,
also muss etwas gesendet werden; die Epoche ist offensichtlich keine echte Zeit,
während `time.Now()` wie eine gerade geänderte Datei aussähe und jedes Sync-Werkzeug
bei jedem Lauf alles kopieren ließe.
