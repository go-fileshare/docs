通常、1 つの fileshare プロセスが、1 つのアカウントとして全員にサービスを提供します。
誰に何を許可するかは fileshare が決め、作成されるファイルはすべてそのアカウントの所有になります。
ディレクトリ共有は、これに代えて**各人として**提供することもできます。ログインした人の
ファイルは、その人の uid、gid、グループで動作するプロセスによって開かれるため、
ツリーのパーミッションはカーネルが適用し、作成されたものはその人の所有になります。

```hcl
identity {
  service_user = "fileshare"   # the account the protocols are served as
  min_uid      = 1000          # the default; uid 0 is refused whatever this says
  min_gid      = 1000
  deny_uids    = [65534]
  idle         = "2m"          # how long an unused worker is kept
}

share "home" {
  directory = "/srv/home"
  identity  = "system"
}
```

## 3 つのプロセス {#three-processes}

`fileshare serve` は**root で起動**しなければなりません。root のままでいるのは、
各人のワーカーを起動するためだけです。ネットワークに面する処理はすべて、
2 つ目のプロセスで `service_user` として動作します。

| プロセス | 実行ユーザー | 役割 |
|---|---|---|
| **ランチャー**(`fileshare serve`) | root | リスナーをバインドし、フロントを起動し、フロントの要求に応じてワーカーを起動する。プロトコルは一切話さない。 |
| **フロント** | `service_user`(そのアカウントのグループを持つ) | これまでの `serve` と同様に、プロトコルを話して認証を行う。このような共有については、uid やパスではなく、ランチャーに**人と共有**を求める。 |
| **ワーカー** | その人 | ランチャーが渡したソケットを通じて、フロントに 1 つの共有を提供する |

ワーカーは最初に、期待どおりの uid、gid、グループで動作していること、そして
`setuid(0)` が失敗することを確認します。そのあとで初めて `os.Root` を通じてツリーを開きます。
1 つのワーカーが、その人のその共有へのすべての接続を、SFTP と WebDAV の両方にわたって処理し、
`idle` の間まったく使われなければ停止します。サーバーが停止すると、ワーカーも一緒に停止します。

## システム上で人とは誰か {#who-a-person-is-on-this-system}

ランチャーは、人を**自ら**次の順序で解決します。

1. `uidNumber` と `gidNumber` を持っていれば、**ディレクトリ**:
   - `user` ブロックの `attributes = { uidNumber = "2001", gidNumber = "2001" }`
   - `attributes = ["uidNumber", "gidNumber"]` を指定した LDAP ソース
   - SQL ソースの `users_attributes` クエリ

   補助グループは、その人を一覧に含むグループ(`group` ブロックの `members`、`memberUid`)と、
   その人が名指しするグループ(`memberOf`)で、いずれも `gidNumber` によって決まります。
   `gidNumber` のないグループはシステムグループではありません。
2. 名前による **`/etc/passwd` と `/etc/group`**。

**拒否されるもの**: uid 0、gid 0、`(uid_t)-1`、`min_uid` 未満の uid、`min_gid` 未満のプライマリ gid、
`deny_uids` にあるすべての uid。`min_gid` 未満の補助グループは除外され、ログにその旨が記録されます。
どちらにも見つからない人も拒否されます。共有の代替アカウントはありません。
ID プロバイダーが身元を保証する人にワーカーが割り当てられるのは、
その名前をローカル名にする [`local_names`]({{< relref "/configuration/identity.md" >}}) がある場合だけです。

したがって、乗っ取られたフロントが要求できるのは、存在して許可されている人の、
存在する共有に限られます。**誰が**認証されたかを決めるのは依然としてフロントであり、
ランチャーにはそれを確認する手段がありません。

## クライアントから見えるもの {#what-a-client-sees}

| | SFTP | WebDAV |
|---|---|---|
| ワーカーの確保 | ログイン時に、接続全体で | リクエストごと。ロックはワーカーが存続する間は保持される |
| ランチャーがその人を拒否した場合 | その人のツリーに共有が表示されない(何も入っていないツリーはログイン拒否となる) | `403` |
| ワーカーを起動できない場合 | 同上 | `503` |

理由はサーバーのログに記録され、クライアントには返されません。

{{< callout type="warning" >}}
**SMB、NFS、S3 ではまだ使えません**

これらはそのような共有を拒否し、[`check`]({{< relref "/configuration/check.md" >}})
がそのことを伝えます。SMB と NFS では、各ライブラリでセッションごとのファイルシステムが必要です。
NFS は `AUTH_UNIX` がクライアント自身の主張にすぎないため(RFC 5531 §14)、
Kerberos の下でのみ対応する予定です。
{{< /callout >}}

## システムに求めるもの {#what-it-asks-of-the-system}

- **Unix**: Linux、BSD 系、macOS。Windows では共有は拒否されます。
- **`service_user` が読み取れること**: フロントが読むため、設定と、そこで名指しされるすべての
  ファイル(パスワードファイル、ホスト鍵、証明書)。
- **各人が実行できること**: 各ワーカーがその人としてバイナリを実行するため、バイナリ。
- そのような共有を追加または変更するには**再起動**が必要です。ランチャーは設定を
  一度だけ読み込み、フロントに提供させるのではなく、知らない共有を拒否します。
- `--isolate` とは併用できません。

設計と、それぞれの選択の理由は
[docs/identity.md](https://github.com/go-fileshare/fileshare/blob/main/docs/identity.md)に書かれています。
