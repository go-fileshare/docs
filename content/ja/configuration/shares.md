共有が提供するのは、**ディスクイメージ**、**デバイス**ノード、**ホストのディレクトリ**の
3 つのうちの 1 つです。イメージとデバイスにはファイルシステムが含まれており、このプログラムが
自分で読み取ります。ディレクトリはホスト自身のものです。

## イメージと、その中のファイルシステム {#an-image-and-the-filesystem-inside-it}

イメージの中のファイルシステムは、宣言されるのではなく**判別されます**。
[`go-filesystems/detect`](https://github.com/go-filesystems/detect) がマジックを読み取り、
それを扱うドライバーを返します。対象は **fat32、exfat、ext4、ntfs、ufs、
iso9660、squashfs、hfsplus** で、どのドライバーも同じ形、
つまりオフセット 0 にファイルシステムがある `OpenReader(io.ReaderAt, int64)` です。

## 判別できない 4 つ {#the-four-that-cannot-be-sniffed}

**apfs、btrfs、xfs、zfs** はそれぞれ*ディスク*イメージを開いて**パーティション**を選ぶため、
オフセット 0 には見つけられるマジックがありません。共有側でどれを使うかを指定します。

```hcl
share "photos" {
  image      = "/srv/disk.img"
  filesystem = "xfs"
  partition  = 2       # or leave it out: the driver takes the first data partition
}
```

## HFS+ イメージは書き込み可能 {#hfsplus-images-are-writable}

v0.44.0(hfsplus v0.9.0)以降、HFS+ を含むイメージの共有は、FAT、exFAT、ext4 と同様に
書き込み可能で開かれます。クライアントはファイルを作成、変更、削除でき、設定した時刻、
モード、所有者も保存されます。以前は HFS+ イメージは読み取り専用で開かれていました。
イメージは共有を開くときにメモリへ読み込まれ、変更のたびにファイルへ書き戻されます。

**コスト。** hfsplus v0.9.0 はイメージ全体をメモリに保持し、操作(作成、書き込み、名前変更、
`Chtimes`)のたびにイメージ全体を書き直します。そのため共有のメモリ使用量はイメージの
大きさに等しく、変更ごとの I/O も同じです(根本的な解決は go-filesystems/hfsplus#33)。
したがって共有が HFS+ イメージを書き込み可能で開くのは `hfsplus_writable_max` までで、
既定は 256 MiB です(`"0"` は常に開かない。バイト数、または K、M、G、T を付けた値):

```hcl
share "mac" {
  image                = "/srv/mac.img"
  hfsplus_writable_max = "256M"
}
```

これを超える場合、またはサイズが不明な場合、共有は**読み取り専用**で開かれます(範囲読み取りと
時刻は引き続き使えます)。サーバーはイメージ、サイズ、上限を示す 1 行を出力します。

```text
/srv/mac.img is an HFS+ volume and it is 1073741824 bytes, over hfsplus_writable_max (268435456 bytes): a writable HFS+ image is held in memory and rewritten whole on every change, so mac is read-only
```

**ジャーナル付き**のボリューム(`hdiutil create -fs "Journaled HFS+"` や macOS が作成するもの)は、
ジャーナルが空のときだけ書き込まれます。これは正常にアンマウントした後の状態です。
トランザクションを含むジャーナル、または検証できないジャーナルは、サーバーが書き込んだ内容の
上から macOS が再生してしまうため、ドライバーはこれを拒否し、**共有は代わりに読み取り専用で
開かれます**。サーバーは起動を続けます。共有を開くときに、イメージ、共有、理由を示す
1 行を出力します。

```text
/srv/mac.img is an HFS+ volume and its journal holds transactions (hfsplus: journaled volume with a journal that is not empty: transactions pending (start 17408, end 34816)), so mac is read-only
```

そのような共有を書き込み可能にするには、先にジャーナルを再生させます。イメージを Mac で
マウントして正常に取り出すか、`fsck_hfs` を実行してください。(ドライバーにはイメージを
メモリに載せずにジャーナルを調べる方法がないため、この場合だけは上限までイメージを読み込んでから
フォールバックします。)`read_only = true` の共有、デバイス、パーティションは
書き込み可能でのオープンを試みません。

**ほかの書き込み側。** イメージは全体が書き戻されるため、2 つ目の書き込み側は次の書き戻しで
上書きされます。書き込み可能でのオープンはイメージに排他的な助言ロック `flock`
(Linux、macOS、BSD)を取ります。別のプロセス(たとえば同じイメージを使うもう 1 つの fileshare)が
保持している場合、共有は読み取り専用で開かれ、その旨を出力します。ロックは助言的なので
macOS のマウントはこれを取らず、ほかのプラットフォームにはロックがありません。

⛔ **マウント中のイメージに書き込まないでください**。このサーバーでも他のものでも同じです。
互いの変更を知りません。ほかに何も開いていないイメージを提供してください。

## OS がマウントしている書き込み可能イメージは読み取り専用で提供される {#an-image-the-os-has-mounted}

v0.45.0 以降、書き込み可能なイメージ共有（FAT32、exFAT、ext4、UFS、btrfs、XFS、ZFS、HFS+ など、ドライバーを問いません）を書き込み用に開く前に、サーバーはそのイメージを OS がアタッチまたはマウントしているかどうかを OS に問い合わせます。している場合、共有は**読み取り専用**で開かれ、その旨が記録され、サーバーはイメージ、OS のデバイスとマウント、共有の名前を示す 1 行を出力します。

```text
/srv/disk.img is in use by the OS (/dev/loop3, mounted at /mnt/disk), and a second writer would corrupt it, so disk is read-only
```

上記の助言的な `flock` ではこれを防げません。OS はイメージをマウントするときにロックを取らないためです。イメージはデバイスと inode で照合され、パス文字列の比較は行わないので、マウント中のファイルへのシンボリックリンクやハードリンクも検出されます。

| OS | 問い合わせ方法 |
| --- | --- |
| Linux | 各ループデバイスの `/sys/block/loop*/loop/backing_file`（`mount -o loop`、`losetup`、udisks が作るもの）。マウントポイントは `/proc/self/mountinfo` から取得します。アタッチされたループデバイスは、何もマウントされていなくても対象になります。 |
| macOS | `hdiutil info -plist`。アタッチ済みの各イメージの `image-path` を、1 回の読み込みにつき 1 回の呼び出しで取得し、15 秒でタイムアウトします。`-nomount` でアタッチしたイメージも対象です。 |
| FreeBSD、その他の BSD、Windows | **検出できません。** 共有はこれまでどおり書き込み可能です。 |

**チェック自体が失敗した場合**（コンテナに `/sys/block` がない、`hdiutil` がない、またはタイムアウトした、出力がプロパティリストではない）、イメージがマウントされているかどうかは誰にも分かりません。`image_mount_unknown` が決めます。

```hcl
share "disk" {
  image               = "/srv/disk.img"
  image_mount_unknown = "read_only"   # 既定値。"write" にするとそれでも書き込み可能で提供する
}
```

既定値は `read_only` です。読み取り専用の共有は原因を示すログ行が付いた目に見える状態で、人が対処できます。マウント下で書き込み可能な共有は双方のデータを壊し、後になるまで誰も気づきません。`write` は、チェックが機能し得ないホスト（sysfs のないコンテナ）で、誰もイメージをマウントしない場合のための設定です。OS がマウントしていると判明したイメージは、この設定にかかわらず読み取り専用です。チェックが読み取れないバッキングパス（権限拒否、シンボリックリンクのループ）は「別のイメージ」ではなく「判定できなかった」として扱われ、同じ設定に従います。存在しないパスだけが無視されます。Linux では、バッキングファイルが削除されたループデバイスは、プロセスが `/dev/loopN` を開ける場合にカーネル自身の記録（`LOOP_GET_STATUS64`）で照合され、開けない場合は照合されません。

**チェックが検出できないもの**

- **共有がイメージを開いた後に行われたマウント。** チェックはイメージを開くときに実行されます。起動時、管理 API で作成された共有、そしてリロードが共有を再構築し（ユーザーやリストの変更）、その間にイメージがマウントされたことを見つけた場合です。その場合、その共有は専用の読み取り専用オープンを受け取ります。何も変更しないリロードは再確認せず、後からの `hdiutil attach` や `mount -o loop` を監視するものもありません。書き込み可能で提供しているイメージをマウントする前に、共有を停止するかサーバーを再起動してください。
- **ループデバイスも `hdiutil` も経由しないマウント。** `qemu-nbd -c`（nbd デバイス）、FUSE マウント（`fuse2fs`、`guestmount`）、イメージを開いている仮想マシンやその他のプログラム。
- 他のオペレーティングシステム（表を参照）と、別のマウント名前空間でアタッチされたループデバイス。
- マウントが原因で読み取り専用になった共有は、マウントがなくなってもリロード後は読み取り専用のままです。再び書き込み用に開くには再起動してください。

## 任意のファイルシステムでのパーティション {#a-partition-for-any-filesystem}

FAT32、ext4、exFAT を含むディスクイメージも、XFS を含むものと同じくらいの頻度で、
先頭にパーティションテーブルを持ちます。ところが検出はオフセット 0 を読み、
パーティション分割されたイメージのそこにあるのは*テーブル*です。そのため先にパーティションを選び、
ドライバーにはそのビューを渡します。

```hcl
share "photos" {
  image           = "/srv/disk.img"
  partition_label = "photos"          # what lsblk calls PARTLABEL
}
```

パーティションの指定方法は 3 通りあり、**指定できるのは 1 つだけ**です。食い違う 2 つを許すと、
コードが先に試したほうが提供されてしまうためです。

| | |
|---|---|
| `partition = 2` | パーティション分割ツールが表示する形式で、1 から数えた番号 |
| `partition_label = "photos"` | GPT のパーティション名 |
| `partition_uuid = "…"` | GPT の一意な GUID。Linux の `PARTUUID` |

{{< callout type="error" >}}
**インデックスは動く**

ディスクの再パーティション、エントリを別の順序で書き込むツール、パーティションが 1 つ少ない状態で
復元されたイメージなどにより、`partition = 2` は**黙って**別のものを指すようになります。
そこにもファイルシステムが見つかってしまうためです。ラベルや UUID はパーティションそのものを
指します。fstab が何年も前にインデックスの使用をやめたのはそのためです。
インデックスは、そのどちらも持たない MBR イメージのために残されています。
{{< /callout >}}

パーティションを選んだ共有は**読み取り専用**になり、起動時にその旨が表示されます。
ドライバーのオフセットはパーティション基準であるのに、下にあるファイルはディスク全体なので、
書き込みは*イメージ*の先頭からそのオフセットの位置に着地してしまいます。
その位置がパーティションテーブルになることも珍しくありません。

## ファイルシステムを指定すると検出が無効になる {#naming-a-filesystem-turns-detection-off}

{{< callout type="error" >}}
**それが狙いであり、同時にリスクでもあります**

イメージは*その*ファイルシステムとして開かれるか、拒否されるかのどちらかです。XFS だと指定された
FAT32 イメージが XFS の共有になることはなく、起動に失敗し、何として開くよう求められたかが表示されます。
{{< /callout >}}

`filesystem` は判別可能なファイルシステムに対しても受け付けられ、その場合は両者が
比較されます。FAT32 イメージに対して `ext4` と指定した共有は、
*the share says ext4 and the image holds fat32* というメッセージで拒否されます。
これにより、誤検出を後から発見するのではなく、その場で拒否できます。
[`check`]({{< relref "/configuration/check.md" >}}) は、名前で指定されたドライバーにアスタリスクを付けます。
その行は認識されたのではなく、主張されたものだからです。

## イメージだけでなくデバイスも {#a-device-not-only-an-image}

```hcl
share "photos" {
  image = "/dev/sda"        # a device node, not a file
}
```

**特権は必要ありません。** ここでは何もマウントしません。
[`go-filesystems`](https://github.com/go-filesystems) のドライバーが ext4、xfs などを
ユーザー空間で読み取るため、`mount(2)` はなく、したがって `CAP_SYS_ADMIN` も不要です。
デバイスを開くのは通常の `open(2)` であり、ノードのパーミッションによって制御されます。

| | 所有者 | モード | 必要な条件 |
|---|---|---|---|
| Linux `/dev/sda` | `root:disk` | 0660 | `disk` グループのメンバーであること |
| macOS `/dev/disk0` | `root:operator` | 0640 | `operator` グループのメンバーであることに加え、フルディスクアクセス |

拒否された場合は、`permission denied` ではなくどのグループが必要かが表示されます。
答えが `sudo` になることはありません。

⛔ **デバイス共有は読み取り専用です。** パーティションを選んだ共有と同じ理由です。
稼働中のディスクに書き込むことは、利用者に代わって決めてよいことではありません。

{{< callout type="error" >}}
**デバイスは排他的に開かれます。これは慎重さではなく、正確さのためです**

カーネルがそのデバイスからファイルシステムをマウントしている場合、ファイルシステムのページキャッシュには
デバイス上よりも新しいメタデータがあります。そのため生の読み取りでは、更新前のディレクトリブロックと
更新後の inode ブロックが並んで見えてしまい、ディスク上にはどの瞬間にも存在しなかった状態になります。
ブロックデバイスへの `O_EXCL` は、「マウントを含め、ほかに誰も使っていない」ことを示すカーネル自身の
プリミティブで、`mkfs` や `fsck` が使っているものです。使用中のデバイスは、名前と理由を示して拒否されます。
{{< /callout >}}

2 つの点は、想定ではなく実測で確かめました。

- デバイスでは `Stat().Size()` が **0** になるため、長さはデバイス自身に問い合わせます。
  末尾へのシークは Linux では答えを返しますが、macOS ではエラーなしで **0** を返します。
  そのため Darwin では代わりに `DKIOCGETBLOCKCOUNT` を使います。
- **raw** ノード(`/dev/rdiskN`、または Linux の `O_DIRECT`)はアラインされていない読み取りを拒否しますが、
  オフセット 11 の 2 バイトのフィールドを読むことこそが FAT BPB の解析です。
  そこでデバイスへの読み取りはブロック全体に切り上げられます。これがないと、
  `/dev/rdisk4` は `unknown filesystem` と報告していました。

## イメージだけでなくディレクトリも {#a-directory-not-only-an-image}

v0.8.0 以降、共有はイメージの代わりに、コンテナーのボリュームなど、ホストのディレクトリを
提供できます。

```hcl
share "photos" {
  directory = "/data/photos"
  allow     = ["@family"]
}
```

これを担うのは [go-filesystems/osfs](https://github.com/go-filesystems/osfs) で、
ツリーには **`os.Root`** 経由でアクセスします。外へ抜ける `..`、絶対パス、外へ向かう
シンボリックリンクは、文字列の判定ではなく、カーネルに支えられたルートによって拒否されます。
クライアントが `/etc` へのリンクを*作成*することはできますが、それをたどるものはありません。
ツリーに置かれた FIFO は、サーバーをハングさせることなく拒否されます。

{{< callout type="error" >}}
**1 つの共有が別の共有を含んではならない(v0.17.0 以降)**

ツリーの中に別の共有のイメージやディレクトリを含むディレクトリ共有は、
**起動時に拒否され**、管理 API でも拒否されます。外側の共有を使える人が、
許可されていないはずの内側の共有を読み書きできてしまうためで、匿名 NFS も例外ではありません。
同じソースを指す 2 つの共有も同様に拒否されます。ただし、1 つのディスクイメージの
異なる 2 つのパーティションは除きます。
{{< /callout >}}

{{< callout type="info" >}}
**イメージのロックの対象外**

イメージのドライバーは 1 つのファイルを所有し、同時に 2 つの呼び出しが来たときの動作を何も保証しません。
そのため[すべてのイメージは 1 つのロックで包まれています]({{< relref "/operations/locking.md" >}})。
ホストのツリーはカーネルのものであり、カーネルは呼び出しごとに直列化すべきものだけを直列化し、
それ以上のことはしません。全クライアントのすべてのファイルの前に 1 つのミューテックスを置けば、
ファイルサーバーとして最も遅い構成になってしまいます。
{{< /callout >}}

⛔ 共有には `image` **または** `directory` のどちらか一方が必要で、両方を指定することも、
どちらも指定しないこともできません。`filesystem` と `partition` はイメージ用です。
これらを指定したディレクトリ共有は拒否されます。指定したということは、その共有がイメージの
つもりだったことを意味するためです。
`read_only = true` はイメージと同様にディレクトリでも機能します。これを指定しながら
`writers` も列挙した共有は、`read_only` が優先されてしまうため拒否されます。

クライアントに通知される容量は、ツリーが置かれているファイルシステムのものです。
取得できないプラットフォームでは 0 のままとなり、プロトコル側はこれを「満杯」ではなく
「不明」として扱います。

## 保存できない時刻を SMB はどう扱うか {#what-smb-does-with-a-time-it-cannot-store}

クライアントが設定した時刻をストレージが保持できない場合、既定では**無視されます**。
v0.42.0 から、共有ごとに `unstorable_times` で選べます。保存できないのは、報告された
値と異なる CreationTime、単独で送られた ChangeTime、イメージに対するアクセス時刻
または更新時刻のうち、時刻を設定できないドライバー(NTFS、APFS、ISO 9660、SquashFS)の
イメージに対するものです(ホストのディレクトリと FAT、exFAT、ext4、HFS+ のイメージはこれらを保存します)。

```hcl
share "photos" {
  directory        = "/data/photos"
  unstorable_times = "log"      # "ignore"(既定)、"refuse"、"log"
}
```

`refuse` はクライアントにエラーを返し、`log` は共有名とパスを記した 1 行を書きます。
共有の種類ごとの正確な場合分けは
[実際のファイル時刻]({{< relref "/protocols/times.md#when-unstorable" >}})を参照してください。
