```hcl
serve "s3" { addr = "0.0.0.0:9000" }
```

Ou en HTTPS, depuis la v0.9.0, avec `tls = true` et un
[bloc `tls`]({{< relref "/security/tls.md" >}}) :

```hcl
serve "s3" {
  addr = "0.0.0.0:9000"
  tls  = true
}
```

Le cinquième protocole, celui qui rend une image accessible depuis tout ce qui
parle le stockage objet — un outil de sauvegarde, une chaîne de traitement de données, `rclone`, le
`fetch()` d'un navigateur. **Rien n'est monté.**

```
GET /                      the shares this person may use, as buckets
GET /photos?list-type=2    the files in that share, as keys
GET /photos/holiday.jpg    the file itself, Range and all
```

## Un partage est un bucket {#a-share-is-a-bucket}

Servi sur la **même arborescence par utilisateur que celle de SFTP** : un système de fichiers dont le niveau
supérieur est l'ensemble des partages que cette personne peut utiliser. Un partage qu'alice ne peut pas utiliser n'est donc pas un bucket
qu'alice peut voir, et les règles d'accès sont appliquées en un seul endroit plutôt que recopiées
dans un second protocole.

{{< callout type="info" >}}
**Un répertoire dans un partage est un préfixe, pas un objet**

C'est ce que croient déjà les clients S3 — ils affichent comme des dossiers les préfixes qui se terminent par
le délimiteur. Un `GET` sur un répertoire répond `NoSuchKey`, car
répondre 200 ferait croire à un client qu'il peut récupérer les octets d'un dossier.
{{< /callout >}}

## Une clé d'accès est un utilisateur ; la clé secrète est son mot de passe {#an-access-key-is-a-user-the-secret-key-is-their-password}

```sh
export AWS_ACCESS_KEY_ID=alice
export AWS_SECRET_ACCESS_KEY=$(cat alice.pw)
aws --endpoint-url http://attic.example.org:9000 s3 ls
```

SigV4 prouve la possession du secret en calculant un HMAC à partir de celui-ci — le
mot de passe ne traverse jamais le réseau, exactement comme avec NTLMv2.

{{< callout type="error" >}}
**L'annuaire doit donc DÉTENIR le mot de passe, et pas seulement le vérifier**

Une source qui ne sait que *vérifier* un mot de passe — une liaison LDAP, une colonne bcrypt
— peut répondre à WebDAV et **ne peut pas** répondre à S3.

Pas non plus une empreinte NT : c'est le MD4 dont SMB peut se servir, et un HMAC
ne peut pas être calculé à partir de lui. **Une identité qui ne détient qu'une empreinte NT sert
SMB et pas S3** — des voisins proches plutôt que la même réponse.
[`check`]({{< relref "/configuration/check.md" >}}) affiche la colonne.
{{< /callout >}}

⛔ Il n'existe aucun accesseur `Password()` dans le programme : le mot de passe n'est
atteint que par `Identity.Derive`, qui prend une dérivation et renvoie
son résultat. Pour S3, la dérivation est l'identité, car le calendrier de clés de SigV4
se trouve dans go-filesystems/s3 ; le secret va à cette vérification de signature,
pour ce seul utilisateur, et nulle part ailleurs.

## Ce qui est servi {#what-is-served}

`ListBuckets`, `HeadBucket`, `ListObjectsV2` avec préfixe, délimiteur, max-keys
et continuation, `HeadObject`, et `GetObject` avec `Range`. SigV4 sous ses deux
formes, en en-tête et présignée.

L'API objet elle-même est
[`go-filesystems/s3`](https://github.com/go-filesystems/s3).

## Ce qui est refusé, et pourquoi {#what-is-refused-and-why}

{{< callout type="warning" >}}
**Les écritures répondent 403**

`PUT`, `POST` et `DELETE` sont refusés avec `AccessDenied` (« this export is
read-only »). fileshare garde le serveur S3 en lecture seule parce qu'un partage qu'une personne
ne peut que lire doit refuser au même endroit que SFTP, et ce n'est pas encore
câblé ; go-filesystems/s3 v0.3.0, sur lequel repose cette version, refuse de toute façon
toutes les écritures. Refuser vaut mieux qu'un objet à moitié écrit.
{{< /callout >}}

{{< callout type="warning" >}}
**Un jeton porteur n'est pas accepté ici**

[OIDC]({{< relref "/protocols/webdav.md" >}}) fonctionne sur WebDAV et nulle part ailleurs. S3 s'authentifie avec
une signature SigV4 — un HMAC sur la requête, sans aucun champ où un jeton porteur
pourrait se loger.

La voie est STS `AssumeRoleWithWebIdentity`, qui échange un jeton OIDC
contre des identifiants temporaires avec lesquels le client signe ensuite. Elle est
servie sur ce listener depuis la v0.50.0 : voir [ci-dessous](#sts).
{{< /callout >}}

Le téléversement en plusieurs parties (multipart), le versionnage, les ACL, les politiques, les règles de cycle de vie, la réplication et
les étiquettes ne sont pas implémentés. Définir l'un d'eux, ou commencer un téléversement
multipart, est une écriture, et répond `AccessDenied` comme toute autre. Un `GET` qui
en demande un (`?versioning`, `?acl`, `?tagging`...) n'est pas distingué :
la requête est ignorée et c'est le listage du bucket ou l'objet qui est renvoyé.
`NotImplemented` répond à un listage autre que `list-type=2`, à toute méthode autre que
`GET` sur `/`, et à une méthode qu'aucune opération ici n'utilise.

## Identifiants temporaires : STS `AssumeRoleWithWebIdentity` {#sts}

Depuis la v0.50.0, le listener S3 répond aussi à l'API STS d'AWS
(`AssumeRoleWithWebIdentity`, version 2011-06-15) : un jeton du fournisseur du
[bloc `oidc`]({{< relref "/protocols/webdav.md" >}}) est échangé contre une clé d'accès, une clé secrète et un jeton de
session qui **expirent**. `aws`, `rclone` et les SDK AWS le parlent comme avec AWS, et personne
ne détient de mot de passe.

```hcl
oidc {
  issuer   = "https://login.example.org"
  audience = "fileshare"
}

serve "s3" {
  addr             = "0.0.0.0:9000"
  tls              = true
  sts              = true      # POST / avec Action=AssumeRoleWithWebIdentity
  sts_duration     = "1h"      # la valeur par défaut, de 15m à 12h
  sts_max_duration = "4h"      # le plus que DurationSeconds peut demander ; par défaut sts_duration
  static_keys      = false     # plus de « la clé d'accès est un utilisateur » : seuls les identifiants temporaires signent
}
```

- **Le jeton** est un jeton d'accès (`typ` `at+jwt`) du fournisseur du bloc `oidc`, pour l'émetteur
  et l'audience de ce bloc — il n'y a pas de seconde configuration de fournisseur. Le jeton d'une
  personne, ou d'une machine : le jeton `client_credentials` de go-authn/bridge pour un client qui
  s'authentifie avec une clé privée (`private_key_jwt`) a `sub` = l'ID du client, qui est le nom ici.
- ⛔ **Il passe la même règle qu'un jeton en WebDAV.** Un jeton valide pour un nom qu'aucune source
  d'ici ne connaît est refusé, sauf `trust_all = true` ou si la règle `oidc:` d'un partage le nomme
  (`allow = ["oidc:user:winpc-17"]`). Les règles du partage décident ensuite de ce qui est visible.
- **La réponse** est `AccessKeyId` (`ASIA…`), `SecretAccessKey`, `SessionToken` et `Expiration`. Les
  requêtes sont signées avec eux et portent le jeton de session dans `x-amz-security-token`,
  **signé**. Ils sont aléatoires, gardés en mémoire seulement et jamais écrits ; un redémarrage les
  termine et le client redemande.
- ⛔ **Durée = min(demandée, ce qu'il reste au jeton).** Les identifiants ne survivent jamais au jeton
  qui les a achetés (`sts_duration`, ou `DurationSeconds` jusqu'à `sts_max_duration`, n'est que le
  plafond). Un jeton auquel il reste **moins de 6 minutes** est refusé avec `ExpiredTokenException` :
  les SDK AWS renouvellent environ 5 minutes avant `Expiration`, et des identifiants plus courts
  seraient renouvelés aussitôt, indéfiniment. Un client présente un jeton frais à chaque échange.
- ⛔ **Une session est jugée à chaque requête** : elle expire ; son jeton de session est lié à sa clé
  d'accès ; elle prend fin quand le fournisseur révoque la personne après l'émission du jeton
  ([signaux partagés]({{< relref "/security/shared-signals.md" >}})) ; et quand la configuration
  n'admet plus le nom.
- `Policy`, `PolicyArns` et un second `WebIdentityToken` sont refusés, et les paramètres vont dans le
  corps du POST, jamais dans l'URL.
- **`static_keys = false`** désactive la voie « la clé d'accès est un utilisateur, la clé secrète est
  son mot de passe ». Il faut `sts = true` : sinon la configuration est refusée au chargement, car un
  listener pour lequel personne ne pourrait signer aurait l'air configuré. Sur une adresse hors
  loopback, `sts` demande `tls = true`, ou `plaintext = true` quand le TLS est terminé en amont.

### Sur une machine sans surveillance : awscred

[`awscred`](https://github.com/go-authn/awscred) v0.1.0 est un `credential_process` AWS pour les
machines qui détiennent une clé privée et aucun mot de passe : il signe un `private_key_jwt`,
obtient un jeton de go-authn/bridge, appelle ce point d'accès et affiche les identifiants comme les
SDK les lisent. Les SDK le relancent avant `Expiration`.

```ini
[profile fileshare]
credential_process = awscred --issuer https://login.example.org --client winpc-17 --key /etc/awscred/winpc-17.pem --sts https://s3.example.org
```

⛔ Sous Unix, `awscred` refuse un fichier de clé lisible par le groupe ou par les autres
(`chmod 600`). Sous Windows, les modes de fichier ne signifient rien : gardez la clé dans le profil
du compte de service ou dans un répertoire dont l'ACL n'admet que ce compte. Une clé dans le magasin
CNG de Windows ou dans un TPM n'est pas encore prise en charge.

### Derrière un proxy : `trusted_proxies`

Derrière le proxy pour lequel existe `plaintext = true`, tous les clients seraient une seule source
pour les limites ci-dessous. Nommez les proxys dans le bloc serve de `s3` :

```hcl
serve "s3" {
  addr            = "127.0.0.1:9000"
  plaintext       = true
  sts             = true
  trusted_proxies = ["10.0.0.2", "10.0.1.0/29"]
}
```

Seule une requête arrivant **d'un** proxy de confiance est crue sur son client, par le saut le plus à
droite de `X-Forwarded-For` qui n'est pas lui-même un proxy de confiance ; de toute autre, l'en-tête
est ignoré.

{{< callout type="warning" >}}
**La liste doit nommer les proxys et rien d'autre**

Un préfixe plus large qu'un hôte (un `/24`, un `/64` IPv6) est accepté — un parc de proxys, un `/29`,
est légitime — et un avertissement est affiché au démarrage : un client qui peut avoir une adresse
dedans choisit son propre `X-Forwarded-For`, et avec lui le seau où il est compté.
{{< /callout >}}

### Limites

- **16 sessions par nom** : la plus ancienne du même nom part d'abord, les sessions des autres noms
  restent (20000 en tout).
- **60 requêtes par minute par adresse source**, avec la réponse `429 Throttling`. Chaque requête
  compte, valide ou non, avant la vérification du jeton. Une source est une adresse IPv4, ou un **/64**
  IPv6.
- Le comptage est en O(1) par requête, sous son propre verrou, dans une minute glissante faite de deux
  générations ; les requêtes S3 avec identifiants ne l'attendent jamais.
- Une source vue dans la dernière minute est comptée tant que la table contient moins de
  **2 × 10000** entrées (la borne, quelle que soit la durée d'un déluge). Une source que la table
  pleine n'a pas vue est comptée dans un seau de débordement de son réseau — son **/48** (IPv6) ou
  **/24** (IPv4), dix fois le débit chacun — de sorte qu'un déluge épuise les seaux des réseaux d'où il
  vient, pas ceux de tout le monde. Les voisins IPv4 derrière un /24 (CGNAT, un campus) partagent un
  seau.
- ⛔ **Au-delà de 1024 réseaux par minute, un seau partagé sert le reste** : un attaquant qui détient
  plus de réseaux l'épuise, et toute source que la table n'a pas déjà vue — **y compris les clients
  existants qui renouvellent environ toutes les heures** — est refusée jusqu'au changement de minute.
  C'est la limite de cette conception.

## Deux limites à connaître avant de le pointer vers quelque chose de volumineux {#two-limits-worth-knowing-before-pointing-it-at-something-large}

**`GetObject` lit l'objet entier en mémoire.** L'interface des pilotes n'offre que
`ReadFile` — ni ouvreur, ni lecteur — il n'y a donc aucune lecture en flux
à utiliser. Une borne, 256 Mio, répond `EntityTooLarge` plutôt que de faire
tomber le processus.

**`LastModified` vaut l'epoch.** `filesystem.Stat` porte `Mode`, `Size` et
`Inode`, et aucune date de modification. Le champ n'est pas facultatif dans le schéma
S3, il faut donc envoyer quelque chose ; l'epoch n'est manifestement pas une vraie date,
alors que `time.Now()` ressemblerait à un fichier qui vient de changer et ferait tout recopier
à chaque outil de synchronisation, à chaque passage.
