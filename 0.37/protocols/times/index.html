Protocols
File times

Real file times

Which shares report each file's own times over NFS, SMB, SFTP and WebDAV, what each protocol says when a time is not recorded, and what happens when a client sets a time over SMB.

Since v0.39.0 a file’s times are the ones its filesystem recorded, not the time of the request. This needs the optional TimesReader capability ofgo-filesystems/interface v0.6.0, which a driver either has or does not.

Which shares report real times

ShareReal times
Directory (host)yes: access, modification, change and, where the host keeps it, birth time, to the nanosecond
FAT imageyes, at FAT’s resolution: modification 2 s, access one day, creation 10 ms; there is no change time
exFAT image (since v0.40.0)yes: creation and modification 10 ms, access 2 s; there is no change time
NTFS image (since v0.40.0)yes: creation, modification, change and access, 100 ns
ext4 image (since v0.40.0)yes: access, modification and change to 1 ns (1 s on 128-byte ext2/ext3 inodes); creation only where the inode is large enough
HFS+ image (since v0.40.0)yes: creation, modification, change and access, 1 s
Other image typesanswered as before
Share served as its people (remote worker)yes, when the worker’s directory is a host directory: the time crosses the worker boundary

A time is compared at the coarser of the format’s resolution and the protocol’s own: SFTP carries whole seconds, a WebDAV getlastmodified whole seconds, SMB 100 ns, NFS 1 ns.

When a time is not recorded

ProtocolWhat is sent
SMB0, “not specified”. A driver without the capability still answers the current time.
NFSAn access or change time that is missing becomes the modification time; a missing modification time becomes the time the server started.
SFTPA missing modification time clears the ACMODTIME flag: the client sees no time rather than a wrong one.
WebDAVcreationdate is the birth time; a time that is not recorded is absent from the answer.

Times a client sets over SMB

Since v0.41.0 (go-filesystems/smb v0.10.0,go-filesystems/smb#45), the access and write times a client sets over SMB(SET_INFO, as touch, robocopy /COPY:T and a copy in Explorer do) are applied to the file, on a directory share. A time of 0 leaves that time as it is; -1 freezes it and -2 resumes it, per open handle.

A time that cannot be stored is ignored by default: the request succeeds and that field is dropped, as Samba does, so that copies which preserve times do not fail. This covers the creation time, a change time sent alone, and any time on a driver that cannot set times.

Choosing what happens: unstorable_times

Since v0.42.0 a share says what happens to such a time, with unstorable_times (the UnstorableTimes option of go-filesystems/smb):

share "attic" {
  directory        = "/srv/attic"
  unstorable_times = "refuse"   # "ignore" (the default), "refuse" or "log"
}
ValueWhat the client hearsWhat is kept
ignore (also when the setting is absent)successthe field is dropped, as Samba does
refuseSTATUS_NOT_SUPPORTED, so a backup tool never believes a time was keptnothing of that request is applied
logsuccessthe field is dropped, and one line per request names the share, the path and the fields, written where the server writes its own lines

Any other value is refused when the configuration is read, with an error that names the share and the three words. The setting belongs to SMB: a share whoseprotocols leave SMB out is refused if it sets it. There is no server-wide default; say it on each share. A share created through the admin API usesignore.

When a time cannot be stored

A request is judged field by field, and one unstorable field is enough: refuse refuses the whole request, log writes its line. A time is unstorable when:

  1. CreationTime is set to a value different from the one the driver reports(or the driver reports none). There is no way to set a creation time. A value equal to the reported one is accepted: there is nothing to change.
  2. ChangeTime is sent alone, with a value different from the reported one. Sent together with an access or write time it is accepted, when the driver can set times, because setting them refreshes the change time to now.
  3. An access or write time, on a share whose driver cannot set times(Chtimes): any real value, equal to the current one or not.

Three things are not decided by the policy. A time of 0 (keep), -1 (freeze) or-2 (resume) is never unstorable. -1 on a driver that can set times but cannot report them (ufs, btrfs, xfs and zfs images) is always STATUS_NOT_SUPPORTED,in every mode: that is a missing capability, not a dropped field. And a request on a read-only share (read_only = true, a device, a share that chose a partition, a person who may not write) is answeredSTATUS_MEDIA_WRITE_PROTECTED before any of this, in every mode.

What a share can store depends on its driver, at the versions this release pins:

ShareCreationTimeChangeTime aloneAccess or write time
Directory (host)unstorable unless equal to the reported birth timeunstorable unless equal to the reported onestored (a ChangeTime sent with it is accepted)
Image, driver with Chtimes: ext4, ufs, btrfs, xfs, zfsunstorable unless equal to the reported one (only ext4 reports one: for the others, always)the samestored (a ChangeTime sent with it is accepted)
Image, FAT or exFAT (since v0.43.0)unstorable unless equal to the reported one (both report one)the samestored at the format’s resolution: FAT write time 2 s (rounded down) and access time the date only; exFAT write time 10 ms and access time 2 s (a ChangeTime sent with it is accepted)
Image, HFS+ (since v0.44.0)unstorable unless equal to the reported one (it reports one)the samestored to the second (a ChangeTime sent with it is accepted) when the share sets hfsplus_writable_max (since v0.45.1; by default it is read-only), and not if the journal made the share read-only
Image, driver without Chtimes: NTFS, APFS, ISO 9660, SquashFSthe same (NTFS reports one; the others never)the same, also when sent with an access or write timealways unstorable

The drivers with Chtimes are osfs (osfs.go:383), ext4 (metadata.go:93), ufs(metadata.go:63), btrfs (fs.go:382), xfs (fs.go:521), zfs(metadata.go:94) and, since v0.43.0, fat32 v0.13.0 and exFAT v0.6.0 (the fullMetadataSetter: their Chmod and Chown return “not supported”, since FAT has no mode bits or owners), so touch -d and cp -p on a FAT or exFAT image share are stored; the others have none. HFS+ has one too: hfsplus v0.8.0 implementsChtimes, Chmod and Chown, and since v0.44.0 (hfsplus v0.9.0) a served HFS+ image can be opened writable, so a time set over SMB is stored, but since v0.45.1 only when the share sets hfsplus_writable_max (by default it is read-only). A journaled image whose journal holds transactions is opened read-only instead, and stores nothing(see HFS+ images are writable).Before v0.42.0 the lock fileshare puts in front of every image driver hid Chtimes, so every image dropped a client’s access and write times, ext4 included; since v0.42.0 it carries Chtimes exactly when the driver has it. NTFS images are read by a read-only driver, so nothing is stored whatever the policy says; the policy decides only what the client is told.

Which clients hit which case: Windows Explorer and robocopy /COPY:T send a CreationTime, which a share of any kind cannot keep unless it is unchanged; Linuxtouch -d and cp -p send only access and write times (the kernel client adds a ChangeTime of “now”), which a directory and a driver with Chtimes store, and a driver without it does not.
