ステータス

このページが説明している fileshare のリリース、各リリースで追加された内容、実際のクライアントで検証済みのもの、まだ実装されていないもの。

このページは fileshare v0.31.1 について説明しています。

セキュリティ: v0.31.0 ではなく v0.31.1 を使ってください

Go 1.27.2 では、govulncheck が fileshare で GO-2026-6809 に到達可能と報告します。crypto/x509 の Certificate.Verify が、既知の侵害された中間証明書を拒否していませんでした。Go 1.26.10 と 1.27.3 で修正されています。より古い Go でビルドした v0.31.0 のリリースバイナリは影響を受けます。 v0.31.1 は Go 1.27.3 でビルドされ、go ディレクティブも 1.27.3 なので、go install は自動的に修正済みのツールチェーンに切り替わります。リリースバイナリは go version -m で go1.27.3 と表示されます。三つの UI も同じ方法で再ビルドされています（portal v0.3.2、console v0.3.5、explorer v0.3.2）。変わったのはツールチェーンだけで、動作は変わりません。

v0.21.0 へのアップグレード

満杯のディレクトリ共有の応答が変わります。EDQUOT(クォータ)とENOSPC は、ボリュームだけでなくすべてのディレクトリ共有で、1 つのエラー「no space left on device (the share is full)」にまとめられました。以前は WebDAV の500、NFS の NFS3ERR_IO だった EDQUOT が、507 と NFS3ERR_NOSPC になり、SFTP のテキストはパスを含まないその文になります。SMB は引き続きアクセス拒否を返します。満杯の共有を参照してください。

v0.20.0 へのアップグレード

プロバイダー側の alice は、ローカルの alice の共有を取得できなくなりました。プロバイダーの名前がそのままローカル名であるサイトは、oidc ブロックにlocal_names = true を追加します(あわせて domains も設定します)。これがないために拒否された名前ごとに、サーバーはその旨のログ行を出力します。

v0.19.0 へのアップグレード

別のマシンの ldap:// を指し、start_tls = true のない users "ldap" ブロックは起動しなくなりました。ldaps:// または StartTLS を使用してください。

v0.17.0 へのアップグレード

ある共有の内側に別の共有がある設定、1 つのソースに 2 つの共有がある設定、共有の内側にアクセスファイル(authorized_keys_file、dsn_file、bind_password_file、ssf の ca_file)がある設定は、起動しなくなりました。エラーには共有とパスが示されます。

v0.9.0 より前からのアップグレード

他のマシンから到達できるアドレスで、誰かが認証する状況において、TLS なしで WebDAV を提供する設定は起動しなくなりました。tls = true と tls ブロックを追加するか、TLS を終端するプロキシの背後であれば plaintext = true を指定してください。TLSを参照してください。

検証済み

以下は、このプロジェクトが作っていないクライアントに実際に行わせたことであり、コードに関する主張ではありません。

  • macOS は、curl が WebDAV 経由で同じイメージに書き込んでいる間に SMB で共有をマウントし、WebDAV が書いた内容を読み戻します。読み取りしか許されていない共有へのBob の WebDAV 書き込みは 403、誤ったパスワードは 401 です。
  • go-smb2(このプロジェクトが作っていないクライアント)は、CI の -race の下で、SMB 経由の 20 の並行読み取りを、WebDAV 経由の 20 と同時に実行します。
  • アクセスルールは、設定だけでなくすべてのプロトコルを通して検査されます。alice は書き込め、bob は書き込めません。これは SMB でも WebDAV でも同じで、NFS にはそもそも共有が提供されません。
  • SFTP 証明書は OpenSSH 自身のクライアントで検証されます。証明書を脇に移すと、同じ鍵も拒否されることも確認されています。
  • 証明書による NFS の ID は、go-filesystems/nfs の CI で実際の Linux クライアント (カーネル 6.17、ktls-utils 0.9)を使って計測されました。平文の MNT と tlshd の落とし穴 はこれで見つかりました。
  • KRL の署名なし形式は計測結果です。OpenSSH 9.6 と 10.3 は署名付き KRL を読み、署名をスキップします(go-authn/krl、両方に対して)。
  • go-authn/bridge の相互運用レーン(#12、#17)は、fileshare v0.13.0 を本物のbridge に対して判定します。KRL、NFS 上の CRL、共有シグナルで失効した WebDAV トークン、スコープで無効化された IdP、共有シグナル上の opkssh です。

まだ実装されていないもの

S3 での書き込み。 PUT と DELETE は 403 を返します。ライブラリは書き込めますが、読み取りしか許されていない人の共有は、SFTP と同じ場所で拒否しなければならず、それがまだ組み込まれていません。中途半端に書かれたオブジェクトよりも、拒否するほうが安全です。

S3 での OIDC トークン。 トークンが使えるのは WebDAV だけです。S3 の通常の方法は STS の AssumeRoleWithWebIdentity で、トークンを一時的な認証情報と交換し、クライアントがそれで署名します。これはベアラートークンを受け入れるのとは別の仕組みであり、実装されていません。

admin ブロックまたは metrics ブロックがある場合の --isolate。 拒否されます。API の変更を適用できる単一のプロセスが存在しないためです。プロトコルごとに 1 プロセスを参照してください。

共有 Linux NFS クライアントでの、証明書によるユーザーごとの人の特定。 Linuxクライアントは証明書をマウントに紐づけるため、そのマウントのすべてのユーザーが、証明書が指名する人として扱われます。これはクライアントの性質であり、その場合の答えは sec=krb5 です。保証できないことを参照してください。

S3 自体は提供済みです。共有はバケットであり、SFTP が使うのと同じユーザーごとのツリー上で提供されます。

計測済みであり、計測結果として記載しているもの

このページの主張のうち、不具合の再現ではなく保険や計測にあたるもので、ソースにもそのように書かれているものです。

  • ラップされていない fat32 ドライバーに対して 8 つの goroutine が -race の下で書き込んでも、現時点ではレースは発生しません。共有ロックは契約に対する保険であり(go-filesystems/interface は、パスベースの並行呼び出しについて何も保証していません)、観測された障害の修正ではありません。
  • ビルドタグごとのサイズは計測されました。hashicorp/go-plugin だけで 13.2 MB かかり、これがプラグインフレームワークを採用しない決め手になりました。また、管理 API が持ち込む gRPC は 11.7 MB で、これが nogrpc が存在する理由です。
  • 独自のグループタグ証明書拡張を設計して Go の X.509 パーサーで計測したところ、証明書全体が拒否されました。そのため、グループは代わりにタグ URI として運ばれます。
