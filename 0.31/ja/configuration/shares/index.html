共有: イメージ、デバイス、ディレクトリ

共有が提供できるもの(ディスクイメージ、デバイス、ホストのディレクトリ)と、そのファイルシステムおよびパーティションの選ばれ方。

共有が提供するのは、ディスクイメージ、デバイスノード、ホストのディレクトリの3 つのうちの 1 つです。イメージとデバイスにはファイルシステムが含まれており、このプログラムが自分で読み取ります。ディレクトリはホスト自身のものです。

イメージと、その中のファイルシステム

イメージの中のファイルシステムは、宣言されるのではなく判別されます。go-filesystems/detect がマジックを読み取り、それを扱うドライバーを返します。対象は fat32、exfat、ext4、ntfs、ufs、iso9660、squashfs、hfsplus で、どのドライバーも同じ形、つまりオフセット 0 にファイルシステムがある OpenReader(io.ReaderAt, int64) です。

判別できない 4 つ

apfs、btrfs、xfs、zfs はそれぞれディスクイメージを開いてパーティションを選ぶため、オフセット 0 には見つけられるマジックがありません。共有側でどれを使うかを指定します。

share "photos" {
  image      = "/srv/disk.img"
  filesystem = "xfs"
  partition  = 2       # or leave it out: the driver takes the first data partition
}

任意のファイルシステムでのパーティション

FAT32、ext4、exFAT を含むディスクイメージも、XFS を含むものと同じくらいの頻度で、先頭にパーティションテーブルを持ちます。ところが検出はオフセット 0 を読み、パーティション分割されたイメージのそこにあるのはテーブルです。そのため先にパーティションを選び、ドライバーにはそのビューを渡します。

share "photos" {
  image           = "/srv/disk.img"
  partition_label = "photos"          # what lsblk calls PARTLABEL
}

パーティションの指定方法は 3 通りあり、指定できるのは 1 つだけです。食い違う 2 つを許すと、コードが先に試したほうが提供されてしまうためです。

partition = 2パーティション分割ツールが表示する形式で、1 から数えた番号
partition_label = "photos"GPT のパーティション名
partition_uuid = "…"GPT の一意な GUID。Linux の PARTUUID

インデックスは動く

ディスクの再パーティション、エントリを別の順序で書き込むツール、パーティションが 1 つ少ない状態で復元されたイメージなどにより、partition = 2 は黙って別のものを指すようになります。そこにもファイルシステムが見つかってしまうためです。ラベルや UUID はパーティションそのものを指します。fstab が何年も前にインデックスの使用をやめたのはそのためです。インデックスは、そのどちらも持たない MBR イメージのために残されています。

パーティションを選んだ共有は読み取り専用になり、起動時にその旨が表示されます。ドライバーのオフセットはパーティション基準であるのに、下にあるファイルはディスク全体なので、書き込みはイメージの先頭からそのオフセットの位置に着地してしまいます。その位置がパーティションテーブルになることも珍しくありません。

ファイルシステムを指定すると検出が無効になる

それが狙いであり、同時にリスクでもあります

イメージはそのファイルシステムとして開かれるか、拒否されるかのどちらかです。XFS だと指定されたFAT32 イメージが XFS の共有になることはなく、起動に失敗し、何として開くよう求められたかが表示されます。

filesystem は判別可能なファイルシステムに対しても受け付けられ、その場合は両者が比較されます。FAT32 イメージに対して ext4 と指定した共有は、the share says ext4 and the image holds fat32 というメッセージで拒否されます。これにより、誤検出を後から発見するのではなく、その場で拒否できます。check は、名前で指定されたドライバーにアスタリスクを付けます。その行は認識されたのではなく、主張されたものだからです。

イメージだけでなくデバイスも 

share "photos" {
  image = "/dev/sda"        # a device node, not a file
}

特権は必要ありません。 ここでは何もマウントしません。go-filesystems のドライバーが ext4、xfs などをユーザー空間で読み取るため、mount(2) はなく、したがって CAP_SYS_ADMIN も不要です。デバイスを開くのは通常の open(2) であり、ノードのパーミッションによって制御されます。

所有者モード必要な条件
Linux /dev/sdaroot:disk0660disk グループのメンバーであること
macOS /dev/disk0root:operator0640operator グループのメンバーであることに加え、フルディスクアクセス

拒否された場合は、permission denied ではなくどのグループが必要かが表示されます。答えが sudo になることはありません。

⛔ デバイス共有は読み取り専用です。 パーティションを選んだ共有と同じ理由です。稼働中のディスクに書き込むことは、利用者に代わって決めてよいことではありません。

デバイスは排他的に開かれます。これは慎重さではなく、正確さのためです

カーネルがそのデバイスからファイルシステムをマウントしている場合、ファイルシステムのページキャッシュにはデバイス上よりも新しいメタデータがあります。そのため生の読み取りでは、更新前のディレクトリブロックと更新後の inode ブロックが並んで見えてしまい、ディスク上にはどの瞬間にも存在しなかった状態になります。ブロックデバイスへの O_EXCL は、「マウントを含め、ほかに誰も使っていない」ことを示すカーネル自身のプリミティブで、mkfs や fsck が使っているものです。使用中のデバイスは、名前と理由を示して拒否されます。

2 つの点は、想定ではなく実測で確かめました。

  • デバイスでは Stat().Size() が 0 になるため、長さはデバイス自身に問い合わせます。末尾へのシークは Linux では答えを返しますが、macOS ではエラーなしで 0 を返します。そのため Darwin では代わりに DKIOCGETBLOCKCOUNT を使います。
  • raw ノード(/dev/rdiskN、または Linux の O_DIRECT)はアラインされていない読み取りを拒否しますが、オフセット 11 の 2 バイトのフィールドを読むことこそが FAT BPB の解析です。そこでデバイスへの読み取りはブロック全体に切り上げられます。これがないと、/dev/rdisk4 は unknown filesystem と報告していました。

イメージだけでなくディレクトリも

v0.8.0 以降、共有はイメージの代わりに、コンテナーのボリュームなど、ホストのディレクトリを提供できます。

share "photos" {
  directory = "/data/photos"
  allow     = ["@family"]
}

これを担うのは go-filesystems/osfs で、ツリーには os.Root 経由でアクセスします。外へ抜ける ..、絶対パス、外へ向かうシンボリックリンクは、文字列の判定ではなく、カーネルに支えられたルートによって拒否されます。クライアントが /etc へのリンクを作成することはできますが、それをたどるものはありません。ツリーに置かれた FIFO は、サーバーをハングさせることなく拒否されます。

1 つの共有が別の共有を含んではならない(v0.17.0 以降)

ツリーの中に別の共有のイメージやディレクトリを含むディレクトリ共有は、起動時に拒否され、管理 API でも拒否されます。外側の共有を使える人が、許可されていないはずの内側の共有を読み書きできてしまうためで、匿名 NFS も例外ではありません。同じソースを指す 2 つの共有も同様に拒否されます。ただし、1 つのディスクイメージの異なる 2 つのパーティションは除きます。

イメージのロックの対象外

イメージのドライバーは 1 つのファイルを所有し、同時に 2 つの呼び出しが来たときの動作を何も保証しません。そのためすべてのイメージは 1 つのロックで包まれています。ホストのツリーはカーネルのものであり、カーネルは呼び出しごとに直列化すべきものだけを直列化し、それ以上のことはしません。全クライアントのすべてのファイルの前に 1 つのミューテックスを置けば、ファイルサーバーとして最も遅い構成になってしまいます。

⛔ 共有には image または directory のどちらか一方が必要で、両方を指定することも、どちらも指定しないこともできません。filesystem と partition はイメージ用です。これらを指定したディレクトリ共有は拒否されます。指定したということは、その共有がイメージのつもりだったことを意味するためです。read_only = true はイメージと同様にディレクトリでも機能します。これを指定しながらwriters も列挙した共有は、read_only が優先されてしまうため拒否されます。

クライアントに通知される容量は、ツリーが置かれているファイルシステムのものです。取得できないプラットフォームでは 0 のままとなり、プロトコル側はこれを「満杯」ではなく「不明」として扱います。
