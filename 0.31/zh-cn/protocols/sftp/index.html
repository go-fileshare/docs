SFTP：密钥或证书

SFTP：密钥或证书

使用公钥或 SSH 证书的 SFTP：本地和提供方的颁发机构、OpenPubkey、域授权、源地址以及撤销。

每个客户端都已经具备它：sftp 随 OpenSSH 一起提供，Finder 和 GNOME可以挂载它，编辑器也支持它。它也是这里唯一形态并不契合的协议：一个人登录后进入的是一个文件系统，而不是一个共享列表。

因此，共享成为为刚刚通过身份验证的人构建的目录树的顶层目录：

$ sftp -i ~/.ssh/id_ed25519 -P 2222 alice@attic
sftp> ls
photos  scratch
sftp> cd photos
sftp> get holiday.jpg

alice 无权使用的共享不是 alice 能看到的目录，而 alice只能读取的共享，会在目录树中就拒绝 alice 的写入，而不是交给本来会允许写入的驱动。

跨两个共享的重命名会被拒绝

那将是在两个映像之间进行一次复制和一次删除，而这在任何地方都不是重命名所承诺的行为。

配置 

host_key_file        = "/etc/fileshare/ssh_host_ed25519_key"
trusted_user_ca_file = "/etc/fileshare/ca.pub"   # 可选

user "alice" {
  authorized_keys_file = "/etc/fileshare/alice.pub"
}

user "carol" {}   # 这里什么都没有：carol 的证书就是其凭据

配置了 trusted_user_ca_file 后，由该颁发机构签发、并在其主体中包含该用户的证书就已足够，因此一个人的访问权限是在别处签发并在别处到期的，有人加入或离开时，这里无需编辑任何文件。

签名、有效期和主体由x/crypto/ssh 的 CertChecker 检查；并已对照 OpenSSH 自己的客户端验证，当其证书被移开后，该客户端同样会拒绝这把密钥。

没有 host_key_file 时，每次启动都会生成新的身份

服务器会说明这一点，而所有以前见过它的客户端都会就密钥变更发出警告，这正是客户端在履行其职责。

针对本主机的证书：域授权

自 v0.22.0 起。EuroHPC 联合平台的 SSH CA （GÉANT / MyAccessID）签发联盟中每个站点都信任的证书。每个证书都在ssh-domain-grant@core.aai.geant.org 扩展中说明它适用于哪些主机。sshd 会忽略该扩展，fileshare 在 v0.22.0 之前也是如此：为他人机器签发的证书在这里同样有效。设置 ssh_domains 后，授权会由go-authn/sshcert 按规范读取、解析和匹配。授权中没有包含本主机任何名称的证书会被拒绝。

trusted_user_ca_file = "/etc/fileshare/efp-ssh-ca.pub"
ssh_domains          = ["files.example.org", "sftp.example.org"]
# ssh_accept_ungranted = true   # 仅当受信任的 CA 从不写入授权时
键
ssh_domains本主机的名称，按授权指明它们的方式书写。只要证书的授权中有一个模式匹配其中一个名称，该证书就会被接受。* 表示单个标签内的一个或多个字符：*.example.org 授权 files.example.org，但不授权 a.files.example.org，而 files-*.example.org 不授权 files-.example.org。比较时忽略大小写。这些是主机名，而不是模式，每个只列出一次，并且至少必须信任一个颁发机构（trusted_user_ca_file，或 oidc 块的 ssh_ca_file）。
ssh_accept_ungranted放行没有授权的证书。默认关闭；没有 ssh_domains 时，因其毫无意义而被拒绝。
证书ssh_domains+ ssh_accept_ungranted无 ssh_domains
授权了 ssh_domains 之一放行放行放行
仅授权了其他主机，或 []拒绝拒绝放行
无授权拒绝放行，并记入日志放行
无法解析的授权（null、[1]、不紧凑……）拒绝拒绝放行

没有 ssh_domains 时，不会读取任何内容，也不会有任何变化。授权是在颁发机构签发的证书上读取的：即 trusted_user_ca_file 的证书，以及提供方的证书（ssh_ca_file）。OpenPubkey 证书由用户自己的密钥签名，因此其中的授权只是用户对自己的说法。它的受众是 opkssh_client_id。普通密钥不携带授权，也不在此规则范围内。

每次拒绝都会连同证书的序列号、密钥 ID 和原因一起记入日志：

sftp: alice: certificate 42 ("alice@efp") refused: its domain grant [login.example.eu] names none of this host's names [files.example.org sftp.example.org]
sftp: alice: certificate 43 ("staff") refused: it has no domain grant (ssh-domain-grant@core.aai.geant.org), and ssh_domains requires one

每项决定也会计入 fileshare_sftp_domain_grant_total{result}，结果为 granted、accepted_ungranted、refused_not_granted、refused_absent 或 refused_malformed。客户端在证明自己持有密钥之前就会出示证书，因此这里统计的是尝试次数，而不是人数。

为什么以拒绝为默认

设想一台信任第二个颁发机构的主机：它自己用于员工的 CA、测试CA、附加到同一文件中的 EFP 预发布 CA，或没有授权的 go-authn/bridge客户端。该颁发机构的证书不携带授权。如果缺少授权意味着“没有限制”，那么这个过滤器在该主机上就什么都过滤不掉。

在这里，没有授权的证书会被拒绝，除非 ssh_accept_ungranted 另有说明。存在但无法解析的授权无论内容如何都会被拒绝：写入授权的颁发机构本意就是限制该证书。go-authn/sshcert 演示了多 CA 场景。

使用 EFP 的 CA

trusted_user_ca_file 即 OpenSSH 的 TrustedUserCAKeys。按照 EFP 的信任页面所述，将 EFP发布于 https://sshca.my-eurohpc.eu/config 的密钥放入其中。该 URL 返回 {"PublicKey": "ssh-ed25519 ..."}；文件中单独一行保存PublicKey 的值：

curl -s https://sshca.my-eurohpc.eu/config | jq -r '.PublicKey' > /etc/fileshare/efp-ssh-ca.pub

然后将 ssh_domains 设置为你的托管实体的授权所使用的名称。EFP证书的唯一主体是 MyAccessID 标识符（<id>@myaccessid.org），因此这就是它登录时使用的用户名。同名且没有自己凭据的 user 块会接收它：

user "u1234@myaccessid.org" {}

使用 go-authn/bridge

设置了 ssh_certificates = true 和ssh_domain_grants = ["files.example.org"] 的go-authn/bridge 客户端（v0.19.0 或更高版本）会签发针对本主机授权的证书。设置 ssh_principal_claim = "voperson_id" 后，其唯一主体是此人的 voperson_id，与 EFP 配置一致，这就是要在此处编写的 user 块。信任 bridge 的 CA，与本服务器信任其他任何 CA 的方式相同：

  • 作为 trusted_user_ca_file，用于本地账户。bridge 在 /ssh/config 以 EFP的格式提供其密钥，因此上面的 curl | jq 命令配合 bridge 的 URL 同样有效；
  • 或作为 oidc 块的 ssh_ca_file，用于由提供方担保的人员。

bridge 的其他客户端不写入授权。如果它们的证书必须在此继续有效，这正是 ssh_accept_ungranted 的用途。但它会放行每个受信任颁发机构的所有 无授权证书，所以最好还是为这些客户端提供授权。

绑定到某个地址的证书

bridge 的 ssh_source_address 会写入 source-address 关键选项，与ssh-keygen -O source-address=... 的效果相同。携带该选项的证书只接受来自这些地址的登录，无论是否设置了 ssh_domains。来自证书所允许地址的登录会被放行，前提是在设置了 ssh_domains 时，其授权也包含本主机。来自任何其他地址的登录会被拒绝。

filesharetrusted_user_ca_fileoidc 的 ssh_ca_file，以及 OpenPubkey
v0.22.0 之前强制执行所有地址均被拒绝
v0.22.0，无 ssh_domains强制执行所有地址均被拒绝
v0.22.0，有 ssh_domains所有地址均被拒绝所有地址均被拒绝
v0.22.1，无论有无 ssh_domains强制执行强制执行

“所有地址均被拒绝”是以拒绝为默认的：证书的限制从未放宽，只是登录丢失了。在 v0.22.1 之前，go-filesystems/sftp 的sshd 会拒绝它交给 fileshare 决定的证书上的任何关键选项；这涵盖提供方的证书、OpenPubkey 证书，以及在设置 ssh_domains 时的所有证书。v0.22.1 构建于 go-filesystems/sftp v0.5.1 之上，其 sshd在那里接受 source-address，并在每条证书路径上依据连接来源的地址（IPv4 或 IPv6）强制执行。

其他任何关键选项（force-command、verify-required 等）都会被拒绝，因为本服务器不会对其采取任何动作。

由身份提供方担保的人员

自 v0.11.0 起，oidc 块也可用于 SFTP，但使用的不是令牌（SSH没有地方放置令牌），而是证书：

oidc {
  issuer           = "https://login.example.org"
  audience         = "fileshare"
  ssh_ca_file      = "/etc/fileshare/bridge-ca.pub"   # go-authn/bridge 的 ssh_ca
  opkssh_client_id = "opkssh"                         # OpenPubkey 登录
  opkssh_max_age   = "24h"                            # 12h、24h、48h、1week
}
  • 由提供方的 SSH CA 签发的证书：authn-bridge ssh-cert 会在通过联盟登录之后写入一份。其主体是此人，其groups@go-authn.org 扩展是此人所属的组，因此oidc:groups: 规则 适用。它不是 trusted_user_ca_file，后者的证书针对本地账户：本地颁发机构的证书若声称拥有提供方的组，则会被视为它所指明的本地账户。
  • OpenPubkey 证书，由 opkssh login 写入：由用户自己的密钥签名，并带有承诺该密钥的 ID 令牌。检查方式与opkssh verify 相同：先由openpubkey 验证器检查（对照提供方已发布的密钥检查其签名、nonce 承诺、客户端 ID 和有效期），再将证书的密钥与令牌中的密钥比对；并且SSH 用户名必须是令牌的用户名，因为这里没有 auth_id 文件可以把二者对应起来：sftp alice@univ-example.fr@files.example.org。opkssh_client_id 应当是专属的客户端 ID，绝不能是其他应用的：ID 令牌会传送到此人登录的每个服务器。

要查看证书所携带的组：

ssh-keygen -L -f ~/.ssh/id_ed25519-cert.pub     # Extensions 部分

并且服务器会在每次联盟登录时说明sftp: alice@univ-a.fr, vouched for by the provider, in groups [...]。

被担保不等于被准入

除非有规则指明某人、trust_all 表示提供方就是目录服务，或者local_names = true 表示提供方的名称就是本服务器的名称且本地账户拥有该名称，否则提供方所担保的人在这里仍然是陌生人，这与令牌在 WebDAV 上所通过的测试相同。没有主体的提供方证书，按格式自身的定义对任何人都有效，因此会被拒绝。

-tags noopenpubkey 会排除 OpenPubkey 验证器（约 2 MB）；此类构建中带有 opkssh_client_id 的配置会被拒绝。

收回证书

证书在登录时检查

在提供方处撤销某人，本身并不会撤销已经签发的证书：该证书在到期之前仍可打开 SFTP，而已经打开的 SFTP会话在那之前也保持打开，因为这些人不在目录服务中，所以重新加载与这些人员无关。窗口期就是证书的有效期：bridge 的 ssh_ca { validity }（默认 12h，最长168h，且不超过 IdP 会话的结束时间）以及这里的 opkssh_max_age。请在客户端重新登录允许的范围内尽可能缩短。自 v0.17.0 起，已经打开的 opkssh会话也会在 opkssh_max_age 时结束，无论证书（由用户自己签名）怎么说。

有两种机制可以关闭该窗口期：

  • 提供方的 KRL（ssh_krl_url）：被撤销的证书在登录时被拒绝，而由它打开的会话的每个操作都会再次查询该列表，包括已打开的文件；
  • 共享信号（ssf）：在 CAEP session-revoked 之前，提供方为此人签发的一切内容都会被拒绝，这是处理不在任何列表中的 OpenPubkey 证书的唯一途径。

两者都以拒绝为默认。

没有密码

提示输入密码的客户端正在做密钥本来要避免的事情。

传输大小与打开的文件

fileshare 会应答 OpenSSH 的 limits@openssh.com（自 v0.25.0 起），因此OpenSSH 的 sftp 每个请求最多读写 255 KiB，而不是32 KiB：使用 OpenSSH 10.3 实测约提升 25%。一个会话最多可同时持有1024 个打开的文件和目录；在目录共享上，每一个都是主机的一个描述符，这个上限可防止单个用户耗尽所有描述符。
