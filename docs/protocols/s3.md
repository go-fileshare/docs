# S3 — a share is a bucket

```hcl
serve "s3" { addr = "0.0.0.0:9000" }
```

The fifth protocol, and the one that makes an image reachable from anything
that speaks object storage — a backup tool, a data pipeline, `rclone`, a
browser's `fetch()`. **Nothing mounts.**

```
GET /                      the shares this person may use, as buckets
GET /photos?list-type=2    the files in that share, as keys
GET /photos/holiday.jpg    the file itself, Range and all
```

## A share is a bucket

Served over the **same per-user tree SFTP uses**: a filesystem whose top level
is the shares this person may use. So a share alice may not use is not a bucket
alice can see, and the access rules are applied in one place rather than copied
into a second protocol.

!!! note "A directory inside a share is a prefix, not an object"
    Which is what S3 clients already believe — they display prefixes ending in
    the delimiter as folders. `GET` of a directory answers `NoSuchKey`, because
    answering 200 would make a client think it can fetch the bytes of a folder.

## An access key is a user; the secret key is their password

```sh
export AWS_ACCESS_KEY_ID=alice
export AWS_SECRET_ACCESS_KEY=$(cat alice.pw)
aws --endpoint-url http://attic.example.org:9000 s3 ls
```

SigV4 proves possession of the secret by computing an HMAC from it — the
password never crosses the wire, exactly as with NTLMv2.

!!! danger "So the directory must HOLD the password, not merely check it"
    A source that can only *verify* a password — an LDAP bind, a bcrypt column
    — can answer WebDAV and **cannot** answer S3.

    And not an NT hash either: that is the MD4 SMB can work from, and an HMAC
    cannot be computed from it. **An identity holding only an NT hash serves
    SMB and not S3** — near neighbours rather than the same answer.
    [`check`](../configuration/check.md) prints the column.

⛔ The secret never leaves the directory. `Identity.Derive` runs the key
schedule over the password and returns only the result, which is why there is
no `Password()` accessor anywhere in the program.

## What is served

`ListBuckets`, `HeadBucket`, `ListObjectsV2` with prefix, delimiter, max-keys
and continuation, `HeadObject`, and `GetObject` with `Range`. SigV4 in both
forms, header and presigned.

The object API itself is
[`go-filesystems/s3`](https://github.com/go-filesystems/s3).

## What is refused, and why

!!! warning "Writes answer 403"
    `PUT` and `DELETE` are refused. The library can write, but a share a person
    may only read has to refuse at the same place SFTP does, and that is not
    wired yet. Refusing beats a half-written object.

!!! warning "A bearer token is not accepted here"
    [OIDC](webdav.md) works over WebDAV and nowhere else. S3 authenticates with
    a SigV4 signature — an HMAC over the request, with no field a bearer token
    fits in.

    The usual route is STS `AssumeRoleWithWebIdentity`, which exchanges an OIDC
    token for temporary credentials the client then signs with. That is a
    different mechanism, and it is **not implemented**.

Multipart upload, versioning, ACLs, policies, lifecycle rules, replication and
tagging are refused by name. A client that asks gets `NotImplemented`, which is
what makes it fall back to a single `PUT` rather than failing at the end of a
5 GB one.

## Two limits worth knowing before pointing it at something large

**`GetObject` reads the whole object into memory.** The driver interface offers
`ReadFile` and nothing else — no opener, no reader — so there is no streaming
read to use. A bound answers `EntityTooLarge` rather than taking the process
down.

**`LastModified` is the epoch.** `filesystem.Stat` carries `Mode`, `Size` and
`Inode`, and no modification time at all. The field is not optional in the S3
schema, so something must be sent; the epoch is obviously not a real time,
where `time.Now()` would look like a file that just changed and make every sync
tool copy everything, every run.
